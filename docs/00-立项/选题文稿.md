# 校园失物招领与认领审核系统

**一句话描述：** 把"丢了东西在群里刷屏、捡到东西没处交"变成一条可核验的流程——拾取者登记、失主检索、认领申请、双人审核、交接核销，每一步都留痕，冒领会被拦在交接之前。

本组拟设计一款面向高校校园的失物招领与认领审核系统。核心判断是：**校园失物招领真正的难点不是"信息不聚合"，而是"认领无法核验"。** 今天的失物信息散在班级群、校园墙、保卫处登记簿里，聚合能解决"看见"，但解决不了"证明东西是你的"——任何人只要说"那是我丢的"，拾取者就没有办法分辨，于是出现两种失败：要么东西一直压在拾取者手里（不敢给），要么给错了人（真失主找不回）。

因此本系统把设计重心放在**认领审核链路**上：失主提交认领时必须回答发布方预留的特征核验问题；拾取者初审，保卫处终审，两关都过才生成一次性交接码；线下凭码核销，状态才落到"已交接"。配套的举报、信用分、申诉与统计，是为了让这条链路在真实校园里跑得下去——有人会虚报，会冒领，会恶意举报。

本期聚焦"发布—检索—认领—审核—交接"主链路，不做二手交易、不做快递代取、不做跨校流转。

> 本文保留立项期资料。现行认领与交接规则以 [CR-005](../02-需求规约/变更记录.md) 修订后的 [SRS](../02-需求规约/SRS-v1.0.md) 为准。

## 一　选题背景与目标用户

### 1.1 问题

在一所两万人的校园里，每天都有东西丢：校园卡、雨伞、耳机、水杯、钥匙、充电宝、证件、教材。现有做法无非三条，每条都卡在同一个地方：

| 现有做法 | 它能做到 | 它卡在哪 |
|---|---|---|
| 班级群 / 年级群刷屏 | 有人看见 | 消息三小时就被刷走；发的人重复发，看的人被动接收 |
| 校园墙、二手群转发 | 覆盖广 | 没有结构，找不回；谁都能私聊，无法验证身份 |
| 保卫处失物登记簿 | 权威、集中 | 只在工作时间、只在固定窗口；失主基本不会去看；认领靠自述 |

由此产生三个可观察的损失：

1. **东西回不去。** 拾取者捡到东西，交到保卫处嫌麻烦，自己留着又怕担责任，最后放在抽屉里过期。
2. **给错了人。** 拾取者在群里说"捡到一个黑色耳机"，立刻有五六个人来认领，谁说得像就给谁；真失主反而因为"不好意思争"而放弃。
3. **个人信息裸奔。** 失主为了让人联系，把手机号、学号、甚至身份证照片发在群里，撤不回来。

### 1.2 目标用户

| 用户 | 典型场景 | 核心诉求 |
|---|---|---|
| **主要：失主（学生）** | 昨天在图书馆丢了校园卡，今天才想起来找 | 能用"在哪丢的、大概什么时候、什么特征"搜到，并且能证明是我的 |
| **主要：拾取者（学生 / 后勤人员）** | 在教学楼捡到一部手机，想还给失主但不想被骚扰 | 登记一次就有人管；不用公开自己的联系方式；交接有凭证 |
| **主要：保卫处 / 失物招领处管理员** | 每天处理十几条认领申请，还要应付冒领纠纷 | 一个队列看完所有待办；审核有依据；争议有记录 |
| 次要：系统管理员（课程项目内由团队兼任） | 维护分类与地点、处理举报、看运行情况 | 数据能改、异常能发现、操作有审计 |

### 1.3 为什么这是一道"非玩具题"

单表 CRUD 的失物招领是"发一条、查一条、删一条"。本题的复杂度来自四处，且每一处都能造出可断言的测试用例：

| 难点 | 具体表现 | 对应设计 |
|---|---|---|
| **认领要能核验** | 凭什么相信申请人是失主 | 特征核验问题 + 双人审核 + 交接码核销 |
| **状态要能流转** | 同一条发布同时被 5 个人申请，谁先谁后 | 发布状态机 + 申请状态机 + 并发互斥（唯一约束 + 乐观锁） |
| **信息要能分级** | 手机号、证件照不能人人可见 | 字段级脱敏 + 角色可见性 + 图片遮蔽 |
| **行为要能追责** | 冒领、虚假发布、恶意举报 | 信用分 + 举报处置 + 申诉 + 审计日志 |

## 二　既有设施与数据来源

本项目的功能点锚定在**真实存在的校园设施与公开协议**上，不假设不存在的接口。立项阶段对每一项做了可行性判定，判定为"需探测"的项在 `probe/` 下有可复跑脚本（结论见第十五节）。

| 数据 / 能力 | 来源 | 授权方式 | 关键字段或约定 | 支撑功能 |
|---|---|---|---|---|
| 实名身份（学工号、姓名、院系） | 学校统一身份认证（OAuth2 授权码 / CAS） | 授权码换 token | `userid`、`name`、`department` | FR-1 登录、FR-2 拾取者认证 |
| 物品图片存储 | 对象存储（MinIO 自建 / 云 OSS） | 预签名 URL，有效期 10 分钟 | `object_key`、`content_type`、`size` | FR-6 图片上传与遮蔽 |
| 认领结果通知 | 微信服务号模板消息 / 企业微信应用消息 | 用户扫码绑定，服务端持 token | `template_id`、`openid`、`data` | FR-18、FR-23 |
| 通知兜底 | 邮件 SMTP | 全局一个发信账号 | 收件人、主题、正文 | FR-23 |
| 交接码短信（可选） | 短信服务商 HTTP 接口 | 服务端签名 | 手机号、模板参数 | FR-17（v0.3 可选） |
| 敏感词与内容安全（可选） | 第三方内容安全 API | 服务端 AK/SK | `text` → 命中词与风险等级 | FR-8（v0.3 可选） |
| 校园卡挂失状态（可选） | 校园卡系统 / 一卡通接口 | 需保卫处授权 | 卡号状态 | FR-8 校验（v0.3 可选） |

**三条必须写进设计文档的事实：**

1. **学校统一身份认证是唯一的实名来源。** 失物招领的价值建立在"申请人是真人、且是本校学生"上；没有学工号，审核员无法回溯，信用分也无法挂靠。因此登录必须走学校认证，**不提供自建密码体系**（仅演示环境提供本地账号兜底，见 R10）。
2. **图片里经常出现证件号与手机号。** 实测样本（学生自摄的校园卡、身份证、快递面单）中，正反面照片占比高；系统必须在入库时就做遮蔽，而不是"提醒用户打码"——用户不会打。
3. **通知只能"尽力送达"。** 微信模板消息受用户是否关注、额度与平台策略影响；邮件可能进垃圾箱。因此通知是**尽力而为 + 站内消息兜底**，审核结论以站内消息为准，不能把"发过通知"当作"用户已知情"。

## 三　核心功能

系统功能分六组，共 **27 项功能需求（FR）**。每项标注具体行为与验收口径。

### 3.1 身份与账号（组 1）

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-1 | 校园统一身份认证登录 | OAuth2 授权码模式，回调换 token，解析学工号作为系统唯一身份；不新建密码体系；会话 8 小时过期 | 同一学工号重复登录不产生第二个账号；token 失效后接口返回 401 并引导重新登录 |
| FR-2 | 拾取者实名认证 | 学生可申请拾取者角色：填联系方式、可交接地点、承诺书；由审核员核验后授予；认证通过后角色叠加（同一账号既是失主也是拾取者） | 未认证账号不能发布招领；认证被拒时给出理由；认证状态变更写审计 |
| FR-3 | 联系方式可见性与资料维护 | 手机号、微信号默认仅"审核员 + 已通过终审的申请人"可见；用户可改可交接地点、可关闭站内私信 | 匿名与普通用户读到的手机号一律为 `138****8000` 形式；关闭私信后对方发送返回 403 |

### 3.2 发布与内容治理（组 2）

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-4 | 发布失物信息 | 填标题、分类、丢失地点、丢失时间区间、特征描述、图片（≤5 张）、是否愿意公开悬赏说明 | 发布后进入"待审核"；v0.1 由系统自动通过（命中敏感词除外），v0.2 起可切换为人工审核 |
| FR-5 | 发布招领信息 | 除 FR-4 字段外，必须设置至少 1 个**特征核验问题**（例如"耳机盒内侧贴了什么"）与其答案；答案对失主不可见 | 未设置核验问题不能发布招领；答案只出现在初审页与终审页 |
| FR-6 | 图片上传与敏感信息遮蔽 | 图片存对象存储，入库前做两件事：压缩到长边 1600px；对疑似证件区域做高斯模糊（v0.1 用整图轻度模糊 + 审核员看原图，v0.3 接 OCR 定位） | 列表页返回的是模糊图 URL；原图 URL 仅审核员与本人可取，且为 10 分钟预签名 |
| FR-7 | 编辑、下架与关闭发布 | 本人可编辑未进入"认领中"的发布；可随时下架（不再对外可见）；已交接后自动关闭 | 已进入"认领中"的发布禁止改特征描述与图片（防串供）；下架后检索结果中不再出现 |
| FR-8 | 发布前校验 | 必填校验；手机号/身份证号出现在**描述文本**中时拦截并提示改为在联系方式字段填写；命中敏感词表时转人工审核 | 描述中含 18 位身份证号时提交失败，提示指向具体字段；敏感词命中后状态为"待审核"而非"公示中" |

### 3.3 检索与匹配（组 3）

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-9 | 分类 / 地点 / 时间多维浏览 | 一级分类（证件卡类、电子设备、书籍资料、衣物饰品、钥匙、其他）× 地点（按校区—楼栋两级）× 时间区间；结果按"丢失/拾取时间倒序" | 三个维度组合筛选结果正确；空结果给出"缩小范围"建议而不是空白页 |
| FR-10 | 关键词检索与筛选 | 标题 + 描述 + 特征全文检索；支持"仅看招领 / 仅看失物""仅看未认领"；游标分页 | 1 万条数据下 P95 ≤800ms（NFR-1）；中文分词命中"校园卡"与"饭卡"同义 |
| FR-11 | 相似物品推荐 | 发布详情页给出"可能相关"列表：同分类 + 地点相近 + 时间相近 + 特征词重合度打分，取 Top5 | 同分类同楼栋 3 天内的失物/招领能互相出现在推荐里；无候选时该区块不显示 |
| FR-12 | 关键词订阅与命中提醒 | 用户订阅关键词（如"校园卡 图书馆"），新发布命中时推一条站内消息，同类 24 小时内合并为一条 | 订阅后新发布命中 1 分钟内产生通知；同一关键词 24 小时内最多 1 条 |

### 3.4 认领与审核（组 4）

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-13 | 提交认领申请 | 选择目标招领发布，填写：认领理由、核验问题答案、可证明所有权的补充材料（如购买记录截图）、期望交接时间 | 同一招领在同一时刻只允许 1 条"进行中"申请，他人再提交返回 409 并提示"该物品已有认领在审核中"；本人不可重复申请；答案错误不直接拒绝，交人工初审 |
| FR-14 | 撤回认领申请 | 申请人在终审通过前可撤回；撤回后释放该发布的其他申请排队状态 | 撤回后状态为"已撤回"，不可再改；同一发布可再次申请但计入申请次数 |
| FR-15 | 拾取者初审 | 拾取者看到申请列表（含核验问题答案、申请人脱敏信息），可"建议通过 / 建议拒绝 / 补充提问"；**初审不暴露申请人手机号** | 初审意见必填理由；补充提问后申请状态为"待补充"；同一申请初审只能提交一次 |
| FR-16 | 审核员终审 | 保卫处审核员在队列中处理：查看初审意见、原图、申请人历史（申请次数、通过率、信用分），做"通过 / 驳回 / 要求补充材料"；通过时生成交接码 | 终审通过后发布状态转"认领中"；同物品其余进行中申请（含"待补充"）在事务内一并驳回并通知；驳回必须选原因码 |
| FR-17 | 交接码核销与闭环 | 终审通过生成 6 位一次性交接码（有效期 72 小时），双方都能在详情页看到同一个码；线下见面时一方口述、另一方在系统内输入即完成核销；核销后发布转"已交接" | 同一交接码只能用一次；过期后自动失效并可申请重发（最多 2 次）；核销要求双方均为实名登录态（不校验 IP 与网络位置） |
| FR-18 | 认领结果通知 | 每个关键节点（提交成功、初审完成、终审通过/驳回、交接码生成、交接完成、即将过期）通知相关方 | 通知失败降级到站内消息；站内消息可在列表页回看全部历史 |

### 3.5 状态流转、举报与信用（组 5）

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-19 | 发布状态机与自动过期 | 草稿 → 待审核 → 公示中 → 认领中 → 已交接 → 已关闭；待审核可驳回、公示中可过期、认领中可回退公示中（认领失效） | 非法迁移返回 409；每次迁移写状态日志（操作人、前后状态、原因）；定时任务每天 02:00 扫过期 |
| FR-20 | 举报违规与冒领 | 任何登录用户可举报：虚假信息、冒领、骚扰、违禁品、重复发布；举报需选类型 + 写说明，可附截图 | 同一用户对同一对象只能举报 1 次；举报后对象在审核员队列中出现标记；举报人身份对发布者不可见 |
| FR-21 | 举报处置与信用分 | 审核员处置：警告 / 下架 / 封禁 7 天 / 永久封禁 / 驳回举报；处置结果影响被举报人信用分（初始 100，警告 −10、冒领 −40、虚假发布 −30） | 信用分低于 60 的账号不能发布招领；低于 40 不能提交认领申请；每次扣分写日志并可申诉 |
| FR-22 | 申诉 | 被处置人可在 7 天内提交一次申诉，附材料；由另一名审核员复核（不能是原处置人） | 申诉期间处置不撤销但暂缓升级；同一处置只能申诉一次；复核结论写入原处置记录 |

### 3.6 通知、统计与后台（组 6）

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-23 | 通知渠道与投递降级 | 站内消息为必达通道；用户可绑定微信服务号与邮箱；投递顺序：微信 → 邮件 → 站内，任一成功即止；每次尝试写投递记录 | 绑定后 1 分钟内收到测试消息；主通道失败 3s 内降级；后台可按消息查投递轨迹 |
| FR-24 | 审核工作台与超时升级 | 审核员首页即队列：待终审（按提交时间）、待处置举报、待认证申请；超过 24 小时未处理的条目标黄，超过 48 小时标红并给组长发提醒 | 队列排序稳定；超时标记与统计口径一致；批量通过需二次确认 |
| FR-25 | 统计看板与报表 | 指标：发布量、认领成功率、平均处理时长（提交→终审）、分类分布、地点 Top10、举报处置率、超时率；支持按周/月与校区筛选 | 看板数字与明细可对上（点数字可下钻到列表）；导出 CSV 字段与页面一致 |
| FR-26 | 用户、角色与审计 | RBAC（student / finder / reviewer / admin）+ 资源归属校验；管理操作与敏感数据访问写审计日志（只记元数据，不记物品描述正文） | 越权统一 403 且不泄露资源是否存在；审计可按操作人/对象/时间检索 |
| FR-27 | 基础数据配置 | 分类、地点（校区—楼栋—楼层）、敏感词表、驳回原因码、信用分规则参数；管理员可增删改并停用 | 停用的分类不再出现在发布页，但历史数据仍可读；配置变更写审计 |

## 四　典型使用场景

**场景一：校园卡丢了（主链路）。** 周三上午，李同学在图书馆三楼丢了校园卡。她打开系统，用学校账号登录，在"发布失物"里填：分类=证件卡类、地点=图书馆三楼、时间=今天 8:00–9:00、特征="卡面右下角贴了一张猫咪贴纸，卡套是透明蓝色"。系统提示"描述中不要写学号"，她删掉了学号。发布后立刻检索到一条 20 分钟前的招领："图书馆三楼捡到校园卡一张"。她点"申请认领"，系统问她招领方设置的问题——"卡套颜色？"，她答"透明蓝色"。拾取者（同楼自习的同学）在初审页看到答案，点"建议通过"。下午保卫处审核员在队列里看到这条申请，核对了申请人历史（首次申请、信用分 100），通过。系统生成交接码 `K7F2Q9`，双方各收到一条通知。晚上在图书馆门口，拾取者口述码，李同学在系统里输入，页面同时显示"交接完成"，招领状态转"已交接"。第二天另一位同学想认领同一条，系统直接拒绝并提示"该物品已完成交接"。

**场景二：冒领被拦下。** 有人在群里看到"捡到黑色 AirPods"，直接来系统申请认领，理由写"我丢的"。招领方设置的核验问题是"耳机盒背面刻了什么字"，申请人答"不知道"。拾取者初审写"建议拒绝：未回答核验问题"。审核员看到该申请人 30 天内申请了 6 次、通过 0 次、信用分 72，驳回并扣 40 分。信用分降到 32 后，该账号无法再提交认领申请，需要申诉恢复。

**场景三：证件照不外泄。** 王同学捡到一张身份证，拍照上传。系统检测到图片并做了轻度模糊，列表页展示的是模糊图；只有审核员在终审页能看到原图。失主来认领时，审核员比对姓名与照片，通过后原图仍不对失主开放——失主不需要看自己的证件照，只需要拿到实物。

**场景四：审核员的早上。** 保卫处张老师 9:00 打开工作台：待终审 7 条（其中 2 条标黄，超过 24 小时）、待处置举报 2 条、待认证申请 1 条。她按"提交时间 + 超时标记"依次处理，对一条材料不足的点"要求补充材料"，对一条明显冒领的点"驳回 + 冒领"，对一条被举报的虚假发布点"下架 + 警告"。首页右上角显示今日处理 10 条、平均处理时长 6.2 小时。

**场景五：期末复盘。** 学期末，管理员打开统计看板：本学期发布 486 条，认领成功率 61%，平均处理时长 11.4 小时，证件卡类占 42%，地点 Top3 是图书馆、三教、食堂。导出 CSV 交给保卫处做下学期宣传栏。

## 五　范围与取舍说明

本期范围按"宁小勿大"确定。下表列出评估过的方案与处理结论，理由均可复核。

| 曾评估的方案 | 本期处理 | 理由 |
|---|---|---|
| 二手交易 / 转让 | 不做 | 与失物招领边界重叠，会引入支付与纠纷，超出课程范围 |
| 快递代取、跑腿 | 不做 | 是另一条业务线 |
| 跨校流转 | 不做 | 涉及跨组织身份互认，无授权依据 |
| 图片 OCR 自动识别证件并打码 | v0.1 用"整图轻度模糊 + 审核员看原图"，OCR 列 v0.3 | OCR 定位准确率不可控，误遮关键特征反而影响认领 |
| 自建账号密码 | 不做，只保留演示环境本地账号兜底 | 密码体系意味着额外的找回、防撞库、合规成本，且实名价值不如统一认证 |
| 站内即时聊天 | 不做，只做"一次性交接码 + 审核员可见联系方式" | 聊天会带来骚扰与取证难题；把沟通收敛到审核链路里更安全 |
| 短信通知 | 列为 v0.3 可选 | 有费用与资质门槛，站内 + 微信 + 邮件已够 |
| 悬赏金 / 感谢费 | 只做文本说明，不做支付 | 支付需要商户资质 |
| AI 自动判定认领真伪 | 不做，只做"申请人历史 + 核验问题"辅助 | 认领结论必须由人签字，AI 只提供排序与风险提示 |

## 六　角色与权限控制

系统设 **4 类角色 + 1 个系统角色**，满足"不少于 3 种角色与权限控制"的要求。权限采用 RBAC 叠加资源归属校验，角色可叠加。

| 角色 | 代码 | 主要职责 | 数据权限边界 |
|---|---|---|---|
| 学生（失主 / 浏览者） | `student` | 检索、发布失物、提交认领、接收通知、举报 | 仅本人发布的完整信息；他人联系方式仅脱敏可见 |
| 拾取者 | `finder` | 发布招领、设置核验问题、初审认领、登记保管、核销交接码 | 本人招领的全部申请；申请人手机号不可见（仅审核员可见） |
| 审核员（保卫处 / 失物招领处） | `reviewer` | 终审认领、处置举报、审核拾取者认证、维护基础数据、看看板 | 全域只读 + 审核动作；**不可修改物品内容**；原图可见；操作全审计 |
| 系统管理员 | `admin` | 用户与角色、系统配置、审计检索、运行监控 | 全局配置与用户管理；**默认不读物品描述正文**，需要时走"授权查看 + 审计" |
| 定时任务 | `system` | 自动过期、超时升级、通知补扫、订阅匹配 | 只写系统字段，不代替人工做审核结论 |

**权限实现要点：**

1. **能力与角色分离。** 代码里判定的是能力（`item:publish_found`、`claim:review_final`、`report:dispose`），角色只是能力集合；新增角色不改业务代码。
2. **归属校验在数据层。** 查询一律带 `owner_id` / `reviewer_scope` 过滤；越权统一返回 403，且**不区分"不存在"与"无权限"**（避免被用来探测资源是否存在）。
3. **字段级脱敏。** 手机号、微信号、证件号在序列化层统一脱敏，只有持有 `pii:read` 能力的角色（reviewer）拿到原文，且每次读取写审计。
4. **审核动作不可自审。** 拾取者不能终审自己的招领；审核员不能终审自己提交的认领；申诉复核人不能是原处置人——三条在服务层硬校验。
5. **敏感数据访问留痕。** 原图访问、手机号明文读取、批量导出三类操作必须写审计，审计只记元数据（谁、何时、哪个对象），不记内容正文。

## 九　技术风险与应对

立项阶段识别 **10 项风险**。R1、R2、R3 为重点管理风险，每轮迭代复盘时更新状态。

| 编号 | 风险描述 | 影响 | 应对措施 |
|---|---|---|---|
| R1 | **冒领**：申请人编造特征、串通他人，把别人的东西认走 | 真失主找不回，系统失去信任 | 发布必设核验问题；拾取者初审 + 审核员终审双人把关；交接码一次性核销；申请人历史与信用分作为审核依据；审核结论必须人工签字 |
| R2 | **敏感信息泄露**：证件照、手机号、学号被越权读取或抓包获取 | 合规事故 | 字段级脱敏 + 角色可见性 + 预签名 URL 短有效期 + 图片入库遮蔽 + 敏感访问审计 |
| R3 | **并发冲突**：同一物品多人同时认领，出现"两人都通过" | 数据不一致，线下纠纷 | 发布状态机 + 申请唯一约束（同一发布最多 1 条进行中）+ 乐观锁（`version` 字段）；终审通过时事务内驳回其余申请；并发用例断言 |
| R4 | 通知丢失（服务重启、额度用尽、用户未关注） | 用户不知道审核结果 | 站内消息为必达通道；投递记录 + 幂等消费 + 启动补扫；审核结论页面本身可查 |
| R5 | 举报被滥用（恶意举报竞品/报复） | 正常用户被误伤 | 举报需实名 + 说明 + 次数限额（每人每天 5 条）；处置需人工复核；被处置人可申诉 |
| R6 | 图片存储成本与访问控制 | 存储膨胀或图片被爬 | 入库压缩到 1600px、单图 ≤2MB、单条 ≤5 张；预签名 URL；禁目录遍历；过期归档时删原图 |
| R7 | 数据保留与合规 | 长期保留个人信息有风险 | 180 天自动归档；注销即删个人数据；审计不含正文 |
| R8 | 检索性能退化（数据量上来后 LIKE 全表扫） | 首屏变慢 | SQLite FTS5（开发）/ PostgreSQL `tsvector` + GIN（部署）；分类、地点、时间建组合索引；游标分页不用 OFFSET |
| R9 | 审核人力不足，SLA 不达标 | 认领堆积，体验差 | 队列排序 + 超时升级 + 批量操作；看板暴露超时率；SLA 作为 NFR-5 显式度量 |
| R10 | 学校统一身份认证不可用 / 未授权 | 无法登录，无法演示 | 适配层隔离认证实现；演示环境提供本地账号兜底（显式标记 `auth_source=local`），生产禁用；认证不可用时不阻塞已登录会话 |

## 十三　关键状态图

以下四个关键类的状态迁移用于行为建模，超过"至少两个关键类的状态图"的要求。图形化源文件（Mermaid / PlantUML）在需求建模单元随 `models/state/` 入库。

**发布（失物 / 招领）Item**　草稿 → 待审核 → 公示中 → 认领中 → 已交接 → 已关闭；待审核可驳回；公示中超过 60 天转已过期；本人可随时下架（公示中 → 已关闭）。**已进入"认领中"后禁止修改特征描述与图片**（防串供）。

**认领申请 ClaimApplication**　待初审 → 待终审 → 已通过 → 已完成；待初审可撤回、可转"待补充"、也可直接驳回（初审判为核验不符，立即释放占位）；"待补充"只能补充一次，超 72 小时未补充转已驳回；终审通过后同物品其余进行中申请一并驳回；交接码过期且重发次数用尽时转"已失效"，发布回退"公示中"。

**举报 Report**　待受理 → 处理中 → 已处置 → 已关闭；已处置可被申诉进入"复核中"；复核维持或撤销原处置。

**拾取者认证 FinderCertification**　未认证 → 待审核 → 已认证 → 已冻结；已认证到期需复审；信用分低于阈值自动冻结。

## 十四　过程模型选型论证

本项目选择**增量模型（Incremental）**，并在课程的检查点节奏下落实为两轮"计划—构造—测试—评审"迭代 + 一个承接增量。

| 候选模型 | 适用场景 | 本项目结论 |
|---|---|---|
| 瀑布模型 | 需求稳定、一次性交付 | 不选：审核规则与信用分参数会随试用反馈调整，且课程要求每个检查点有可演示产出 |
| **增量模型** | 需求可分期、每期都能交付可用版本 | **选**：三个增量分别对应"能发布能认领""能治理能通知""能匹配能开放"，与 Milestone / Release 要求一致 |
| 螺旋模型 | 风险高且需每轮完整风险分析 | 不选：风险已识别且集中在审核链路与敏感数据，不必每轮重做完整风险分析 |
| 统一过程 UP | 用例驱动、四阶段、文档较重 | 不选：采纳用例驱动与迭代思想，但四阶段的文档负担与 17 学时检查点节奏不匹配 |
| 敏捷 / Scrum | 需求多变、团队自主 | 部分采纳：看板、Issue 驱动、CI、迭代回顾；不套用完整 Scrum 仪式——4–5 人、8 次课的规模下仪式成本高于收益 |

## 十五　可行性与工程设计价值

### 15.1 已完成的技术可行性验证

立项阶段对**本地可验证**的技术点做了实测（脚本与结果见 `probe/`），对**需要外部授权**的点只做协议层判定，不虚构实测数据。

| 验证项 | 方法 | 结论（2026-11-26 实测） |
|---|---|---|
| 中文全文检索 | SQLite FTS5 + 字符级拆词 + 短语匹配，灌 1 万条后计时 | ✅ 可用。命中数与 `LIKE` 完全一致（966/966）；P95 **12.86 ms**（`LIKE` 51.36 ms），距 800ms 指标 60 倍余量 |
| 并发互斥 | 10 线程并发插入同一招领的进行中申请，断言部分唯一索引生效 | ✅ 10 线程：成功 **1**、冲突 **9**，进行中记录数 **1**；耗时 370 ms |
| 图片遮蔽 | Pillow 缩到 1600px + 高斯模糊，测耗时与体积 | ⚠️ 186.7 KB → 原图 29.9 KB + 遮蔽图 8.0 KB，耗时 **1074.9 ms**（纯色大图，需用真实照片复测） |
| 预签名 URL 过期 | 本地磁盘 + HMAC 签名模拟，验证过期后 403 | 待部署环境验证（依赖 MinIO / OSS） |
| 微信模板消息 | 协议层判定（需 `openid` + `access_token` + 模板审核） | **不可在课程环境实测**，设计为可替换适配器 + 站内兜底 |
| 学校统一身份认证 | 协议层判定（需应用登记与回调备案） | **未获授权**，v0.1 用本地账号兜底，接口契约不变 |

> 诚实原则：外部接口没有实测就写"未实测"，不写"已验证"。这是本组对可行性报告的基本要求。

### 15.2 工程设计价值

系统把"认领审核"设计成一条**带状态机的、可审计的、双人把关的流程**，围绕它可以展开完整的分析、设计与测试：

- **状态机设计**：发布与申请两条状态机如何配合，终审通过时如何原子地驳回其余申请；
- **并发控制**：同一物品的 N 条申请如何只让一条进入终审（唯一约束 + 乐观锁 + 事务）；
- **权限建模**：4 类角色 + 能力判定 + 字段级脱敏 + 归属校验，越权不泄露资源存在性；
- **敏感数据治理**：图片入库遮蔽、原图预签名、访问审计、留存期限与归档；
- **通知可靠性**：多通道降级、投递记录、幂等与补扫；
- **审核质量度量**：SLA、超时率、认领成功率、驳回原因分布，用数据反推流程问题。

### 15.3 合规与数据最小化

只采集审核必需的信息（学工号、姓名、院系、联系方式），不采集身份证号；证件类照片入库即遮蔽；物品信息保留 180 天后自动归档；用户可注销并删除个人数据；审计日志只记元数据，不记物品描述与聊天内容。

## 十六　预期成果与应用价值

预期形成一个可运行的系统原型（后端主链路 + 前端关键页面）与配套课程设计文档，完整展示"登录 → 发布 → 检索 → 申请 → 初审 → 终审 → 交接 → 归档"的链路。

产品价值可通过小范围试用验证，重点观察三个指标：

1. **归还率**：进入系统的招领中，最终完成交接的比例（对照：保卫处登记簿的线下归还率）；
2. **误领率**：交接后被申诉/举报为冒领的比例（这是审核链路是否有效的直接证据）；
3. **处理时长**：从提交申请到终审完成的中位时长（决定用户还愿不愿意用）。

若有推广机会，可在图书馆、三教与食堂三个高频地点试点，与保卫处现有登记簿并行运行一个学期。
