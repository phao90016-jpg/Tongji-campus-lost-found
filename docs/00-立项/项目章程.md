## 2. 项目目标

把校园失物招领从"群里刷屏 + 自述认领"改造成"登记 → 检索 → 申请 → 双人审核 → 交接核销"的可核验流程，
降低"东西回不去"与"给错人"两类损失，同时避免失主与拾取者的个人信息外泄。

**可度量的成功标准**

| 编号 | 标准 | 验证方式 |
|---|---|---|
| G1 | 一条招领从发布到交接完成，全流程在系统内闭环，不依赖站外沟通 | v0.1 演示脚本第 3 节 |
| G2 | 同一招领的 N 条并发认领申请，只有 1 条进入终审 | 自动化并发测试（NFR-2） |
| G3 | 非授权角色读到的手机号一律脱敏，越权返回 403 且不含内容 | 三账号交叉请求（NFR-3） |
| G4 | 通知主通道失败 3s 内降级到下一通道，投递记录可查 | 关闭通道现场演示（NFR-4） |
| G5 | 万条数据检索 P95 ≤800ms | 造数 + 计时（NFR-1） |
| G6 | 三个增量各有一个可运行版本并打 Release | GitHub Releases |

## 3. 范围

**纳入本期**

- 校园统一身份认证登录与拾取者实名认证
- 失物 / 招领发布（含核验问题）、图片上传与遮蔽
- 分类、地点、时间多维浏览与关键词检索
- 认领申请、撤回、拾取者初审、审核员终审、交接码核销
- 发布与申请两条状态机、自动过期
- 举报、处置、信用分、申诉
- 站内消息 + 微信 / 邮件降级投递
- 审核工作台、统计看板、用户与角色、审计日志、基础数据配置

**明确不做（本期）**

- 二手交易、转让、悬赏支付（无商户资质，且偏离主题）
- 快递代取、跑腿
- 跨校流转（涉及跨组织身份互认）
- 站内即时聊天（改为一次性交接码 + 审核员可见联系方式）
- 自建账号密码体系（仅演示环境保留本地兜底）
- AI 自动判定认领真伪（结论必须人工签字）

## 4. 过程模型选型论证

**结论：增量模型（Incremental），落实为两轮迭代 + 一个承接增量。**

选择理由：

1. **需求天然可分期。** "能发布能认领"是价值底线，"能治理能通知"是可用性前提，"能匹配能开放"是加分项；每一期都能独立演示。
2. **与课程的 Milestone / Release 要求一致。** 三个增量对应 `v0.1 / v0.2 / v0.3` 与三个 Milestone。
3. **风险可隔离。** 主要技术风险集中在审核链路（R1 冒领、R3 并发）与敏感数据（R2 泄露），第一轮迭代就把这两块做掉，后续增量不再改主链路。
4. **反馈周期短。** 每次课都是检查点，教师的点评能直接落到下一期。

**不选其他模型的原因**

| 候选 | 结论 |
|---|---|
| 瀑布 | 审核规则与信用分参数会随试用反馈调整，且过程中没有可演示的中间版本 |
| 螺旋 | 风险已识别且集中，不必每轮重做完整风险分析，成本高于收益 |
| 统一过程 UP | 采纳用例驱动与迭代增量的思想，但四阶段文档负担与 17 学时检查点不匹配 |
| 敏捷 / Scrum | 采纳看板、Issue 驱动、CI、迭代回顾等实践；不套用完整 Scrum 仪式——4–5 人、8 次课，仪式成本高于收益 |

## 7. 风险登记册

| 编号 | 风险 | 影响 | 应对 | 责任人 | 状态 |
|---|---|---|---|---|---|
| R1 | 冒领：编造特征、串通他人把别人的东西认走 | 真失主找不回，系统失去信任 | 核验问题 + 双人审核 + 一次性交接码 + 申请人历史与信用分；结论人工签字 | 需求 / 开发 | 监控中 |
| R2 | 敏感信息泄露：证件照、手机号被越权读取 | 合规事故 | 字段级脱敏 + 角色可见性 + 预签名短有效期 + 入库遮蔽 + 访问审计 | 架构 / 开发 | 监控中 |
| R3 | 并发冲突：同一物品多人同时通过审核 | 数据不一致、线下纠纷 | 唯一约束 + 乐观锁 + 终审事务内驳回其余申请 | 开发 | 监控中 |
| R4 | 通知丢失：服务重启、额度用尽、用户未关注 | 用户不知道审核结果 | 站内消息必达 + 投递记录 + 幂等 + 启动补扫 | 开发 | 监控中 |
| R5 | 举报被滥用 | 正常用户被误伤 | 实名举报 + 次数限额 + 人工复核 + 申诉 | 测试 / 需求 | 监控中 |
| R6 | 图片存储成本与访问控制 | 存储膨胀或图片被爬 | 入库压缩、单图 ≤2MB、预签名 URL、归档删原图 | 开发 | 监控中 |
| R7 | 数据保留与合规 | 长期保留个人信息有风险 | 180 天归档、注销即删、审计不含正文 | 项目经理 | 监控中 |
| R8 | 检索性能退化 | 首屏变慢 | FTS5 / tsvector + 组合索引 + 游标分页 | 开发 | 监控中 |
| R9 | 审核人力不足导致 SLA 不达标 | 认领堆积 | 队列排序 + 超时升级 + 批量操作 + 看板暴露超时率 | 项目经理 | 监控中 |
| R10 | 统一身份认证不可用或未授权 | 无法登录、无法演示 | 认证适配层隔离；演示环境本地账号兜底（标记 `auth_source=local`），生产禁用 | 架构 | 监控中 |

> R1、R2、R3 为本项目重点管理的技术风险点，每轮迭代复盘时更新状态。

## 8. 变更管理

- 需求变更一律建 Issue，走"申请 → 评审 → 批准 → 关闭"流程并留痕
- 变更记录登记在 [../02-需求规约/变更记录.md](../02-需求规约/变更记录.md)
- 需求基线以 SRS v1.0 为界，基线后变更须经评审
- 审核规则（信用分阈值、SLA、留存期限）属于"可配置参数"，调整走配置变更 + 评审，不算需求变更

## 9. AI 使用约定

- 遵循课程五总则：验证而非信任、规格先行、人守关卡、为再生成而设计、护密合规
- 所有 AI 产出在 [../08-AI使用/AI使用台账.md](../08-AI使用/AI使用台账.md) 登记
- 架构决策、需求确认、合并放行三处必须由人签字
- 密钥、个人数据、真实学工号与手机号严禁进入提示词
- 演示数据一律使用虚构姓名与 `138****8000` 形式的号码
