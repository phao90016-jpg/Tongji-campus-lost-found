## 1. 引言

### 1.1 目的

定义校园失物招领与认领审核系统的功能与非功能需求，作为设计、测试与验收的基线。
本文档面向课程评审教师、组内开发与测试成员，以及（可选）保卫处业务方。

### 1.2 范围

本期实现"登录 → 发布 → 检索 → 认领申请 → 双人审核 → 领取人确认交接 → 归档"主链路，
含举报、通知、统计与权限治理。不做范围见 [项目章程](../00-立项/项目章程.md) 第 3 节。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 失物发布 LostItem | 失主发布的「我丢了什么」，用于被检索与匹配。认领申请提交到招领发布。 |
| 招领发布 FoundItem | 拾取者发布的"我捡到了什么"，必须携带至少一个核验问题 |
| 核验问题 VerificationQuestion | 招领方预留的、只有真失主能回答的问题（如"卡套颜色"） |
| 认领申请 ClaimApplication | 失主对某条招领提出的所有权主张 |
| 初审 | 由拾取者（发布人）审阅核验证据，提出建议或要求补充材料。 |
| 终审 | 由审核员（保卫处）给出最终结论。通过后申请进入待领取。 |
| 交接确认 HandoverConfirmation | 获准的领取人线下核对实物并收到物品后，登录点击「确认已领取」。系统记录确认人和时间。 |
| 信用分 CreditScore | 账号行为分，初始 100，违规扣减，学期切换时沿用余额，影响发布与申请权限 |
| 脱敏 | 手机号、证件号在非授权角色视图中替换为 `138****8000` 形式 |
| 遮蔽图 | 图片入库时生成的模糊版本，用于公开列表与详情 |

## 2. 总体描述

### 2.1 用户角色

| 角色 | 说明 | 增量 |
|---|---|---|
| 学生（失主 / 浏览者）`student` | 检索、发布失物、提交认领、确认领取、举报、接收通知 | v0.1 |
| 拾取者 `finder` | 发布招领、初审认领、登记保管、查看交接进度（需认证） | v0.1（认证在 v0.2） |
| 审核员 `reviewer` | 由老师承担；终审、超时接手、核实逾期交接，按增量处置举报、审核认证、维护基础数据及查看看板 | v0.1 |
| 学生志愿者 `volunteer` | 查看自己分派案件的脱敏摘要、催办和登记情况 | v0.1 |
| 系统管理员 `admin` | 用户与角色、配置、审计、报表 | v0.2 |
| 定时任务 `system` | 自动过期、超时升级、通知补扫、订阅匹配 | v0.1 |

### 2.2 运行环境

- 浏览器：Chrome / Edge 最近两个大版本；移动端 Safari / 微信内置浏览器
- 服务端：Linux，Python 3.11+
- 数据库：开发 SQLite（FTS5）；部署 PostgreSQL 15+（`tsvector` + GIN）
- 对象存储：开发 MinIO；部署云 OSS

### 2.3 设计与实现约束

| 编号 | 约束 | 来源 |
|---|---|---|
| C-01 | 登录只走学校统一身份认证；演示环境可开本地账号兜底，但必须标记 `auth_source=local` 且生产禁用 | FR-1、R10 |
| C-02 | 手机号和证件号统一由序列化层按权限输出，非授权访问脱敏或省略 | FR-3、REQ-N-003 |
| C-03 | 状态迁移只能经 `services` 层，禁止直接 UPDATE 状态字段 | FR-19、REQ-N-002 |
| C-04 | 密钥、token、真实学工号不得进入代码仓库与提示词 | REQ-N-007 |
| C-05 | 认领归属由审核员判断，系统不得自动通过。定时任务按规则处理未补交等流程超时 | FR-16、R1 |
| C-06 | 图片访问一律走预签名 URL，有效期 ≤10 分钟 | FR-6、REQ-N-003 |

### 4.1 UC-06 发布招领信息并设置核验问题

| 项 | 内容 |
|---|---|
| 参与者 | 拾取者（主）、对象存储（次） |
| 关联需求 | REQ-F-005、REQ-F-006、REQ-F-008 |
| 前置条件 | 已登录且具有 `finder` 角色（v0.1 由管理员在后台直接授予；v0.2 起可自助申请认证，见 UC-02）；信用分 ≥60 |
| 后置条件 | 生成「公示中」招领；命中敏感词时进入「待审核」；核验题与答案按权限保存 |
| 触发 | 拾取者在"发布招领"页点击提交 |

**主成功场景**

1. 拾取者填写标题、分类、拾取地点、拾取时间、特征描述。
2. 拾取者设置核验问题（1–3 个）与答案，并填写交接地点与保管方式。
3. 拾取者上传图片（0–5 张）。
4. 系统校验必填项；扫描描述中的手机号、证件号与敏感词。
5. 系统对图片压缩并生成遮蔽图，原图存对象存储。
6. 系统对答案做哈希后入库，明文只保留在审核员可见的加密字段。
7. 系统创建发布，状态「公示中」，写状态日志与审计。
8. 系统返回发布详情，并提示"已开始接收认领申请"。

**扩展场景**

- 4a 描述中含 18 位身份证号或 11 位手机号：提交失败，高亮对应字段，提示"请在联系方式字段填写，不要写在描述里"。
- 4b 命中敏感词表：发布状态置「待审核」，提示"内容需人工复核，通常 24 小时内完成"。
- 4c 未设置核验问题：提交失败，提示"招领必须设置至少 1 个核验问题，否则无法判断认领人是否为失主"。
- 5a 图片上传失败或超时：发布仍然成功，图片状态置「待重传」，详情页给出重试入口（REQ-N-006）。
- 前置条件不满足（未认证或信用分 <60）：拒绝发布，提示具体原因与恢复路径（申请认证 / 申诉）。

**业务规则**

| 编号 | 规则 |
|---|---|
| BR-06-1 | 招领必须有 ≥1 个核验问题，答案对失主不可见 |
| BR-06-2 | 拾取者不能在自己的招领下提交认领申请 |
| BR-06-3 | 信用分 <60 不能发布招领（可发布失物） |

**活动图**：`models/sequence/act-uc06-publish-found.puml`

### 4.2 UC-15 提交认领申请

| 项 | 内容 |
|---|---|
| 参与者 | 学生（失主） |
| 关联需求 | REQ-F-013、REQ-F-014 |
| 前置条件 | 已登录；信用分 ≥40；目标仍在首个公示周期内并开放申请 |
| 后置条件 | 生成一条「待初审」申请并关联证据版本，占用该物品的唯一进行中名额 |
| 触发 | 失主在招领详情页点击「申请认领」 |

**主成功场景**

1. 失主点击「申请认领」，系统展示招领方设置的核验问题（不展示答案）。
2. 失主填写认领理由、核验答案、可选的补充材料（购买记录截图等）、期望交接时间。
3. 系统在同一物品事务校验：目标状态、公示截止、是否已有进行中申请、本人是否仍有提交资格、是否本人发布、信用分阈值、页面展示的核验信息版本。
4. 系统在事务内插入申请（状态「待初审」）；同时关联证据版本并锁定核验字段。数据库约束保证同一招领同一时刻只有一条进行中申请。
5. 系统写状态日志，向拾取者发"有新认领申请"通知（登录后在站内可查）。
6. 系统返回申请详情与后续流程说明。

**扩展场景**

- 3a 目标处于「认领中」时提示「已有人通过审核，等待领取」。已交接、已关闭、已过期时提示当前状态，并隐藏申请操作。
- 3b 本人已有一条进行中申请：拒绝，返回 409 并给出已有申请的入口。
- 3b1 他人已有一条进行中申请：返回 409 `CLAIM_CONFLICT`，提示"该物品已有认领在审核中，可稍后再试"。
- 3c 目标是本人发布的招领：拒绝（BR-06-2）。
- 3d 信用分 <40：拒绝，提示可申诉恢复。
- 4a 并发提交导致唯一约束冲突：捕获后返回 409，提示"已有申请提交成功"，不产生第二条记录。
- 3e 公示到期时提示「公示已结束」，已有申请仍可从「我的申请」处理。
- 3f 页面展示的核验信息已过时：提示刷新核验信息，保留已填写的理由与材料供用户复核。
- 3g 首次主动撤回后按 §4.5 申请一次，提交时仍校验物品是否空闲。
- 5a 外部投递失败时，站内仍可查申请进度和消息。

**活动图**：`models/sequence/act-uc15-submit-claim.puml`

### 4.3 UC-18 审核员终审认领申请

| 项 | 内容 |
|---|---|
| 参与者 | 值班老师（主）、对象存储（次，核验材料） |
| 关联需求 | REQ-F-015、REQ-F-016、REQ-F-017 |
| 前置条件 | 具备终审权限，申请为「待终审」，本人既非申请人也非发布人 |
| 后置条件 | 通过时申请「已通过，待领取」、发布「认领中」；驳回时申请「已驳回」；退回补充时转「待补充」 |

1. 审核员查看申请提交时的证据版本、补交材料、初审建议和理由，按权限查阅原图和申请人历史。初审建议通过或驳回均进入此步骤。
2. 老师填写结论及理由，通过前校验保管方填写的领取地点和时段仍可用。驳回可选核验不符、材料不足或疑似冒领等原因，申请人的提示不透露标准答案。
3. 系统在同一事务校验权限、状态和版本，记录终审意见与审计。通过时申请转「已通过」，发布转「认领中」。驳回时释放唯一申请名额。操作仅针对当前申请，其他提交在入队时即被拦截。
4. 系统记录站内消息，申请详情展示结论与后续安排。通过后双方可看到领取安排，领取人现场验物后操作 UC-19。

- 待初审超时后，经老师登记缺少拾取者意见的原因并接手，可进入此流程，见 §4.8。
- 要求补充材料时进入 §4.5 的流程，终审要求补交的申请在补交后回待终审。
- 驳回原因属于疑似冒领时，可在 v0.2 登记为待核查的举报候选。
- 其他审核员已处理或申请已经撤回时，提示刷新当前结果，重复提交不得写入第二份结论。
- 写入未完成时事务回滚，申请留在待终审。外部通知异常不影响查看已提交的终审结论。

### 4.4 UC-19 领取人确认交接

| 项 | 内容 |
|---|---|
| 参与者 | 获准申请人（确认）、拾取者或保管方（交付并查看进度）、审核员（逾期核实） |
| 关联需求 | REQ-F-017、REQ-F-019 |
| 前置条件 | 此申请已通过终审并待领取，当前账号为获准申请人 |
| 后置条件 | 记录申请号、物品号、确认账号、确认时间，申请转「已完成」，发布转「已交接」 |

1. 领取人在申请详情查看最新领取地点、日期、可领时段、更新时间及服务点公用渠道，按安排到场验物。变更后通知双方，详情显示新安排。
2. 领取人打开申请详情，点击「确认已领取」。系统在同一事务内验证申请归属和状态，保存唯一确认记录并迁移申请与发布状态，记录状态日志，双方可查结果并收到站内消息。
3. 同一领取人重复请求时返回原有确认结果。保管方和无关账号均无确认权限。若操作没有成功，详情仍显示待领取，恢复网络后可补确认。物品未拿到或不符时，可按详情的安排联系保管方或招领处。
4. 终审通过 72 小时仍未确认时标记逾期、发送一次站内提醒并加入值班待办。逾期申请仍可由领取人补确认。保管方说明实物仍在且审核员核实未交付后，审核员可填写核实说明并结束认领。在同一事务内申请转「已失效」、释放名额，物品按原公示期限回公示或转已过期，通知双方。交付情况有争议时保留待领取状态，供业务方线下核实。
5. 申请确认和审核员结束认领互斥。完成交接 7 天后发布自动关闭。既有交接确认记录可供授权人员追溯。

### 4.5 审核期间的编辑、撤回与补交

- **编辑** · 待初审、待终审、待补充或已通过待领取均为「进行中」。这段时间锁定分类、拾取时地、特征、物品图片、核验题与参考答案，历次申请保留各自证据版本。面向当前申请的交接安排可单独更新，变更通知相关方。核验信息有误时由发布人提交说明，审核员决定继续审核，或记录理由并将尚在审核的申请置为已失效后解锁更正。已通过待领取的，按 UC-19 核实未交付后收尾。下架或关闭需先处理进行中申请。
- **撤回** · 本人在待初审、待终审或待补充时可主动撤回，界面显示剩余提交次数。首次撤回后，物品仍开放受理且无人占位时可附说明重申一次。重申关联原撤回记录，原记录保持原结论。第二次撤回、已驳回或已完成均无常规重申入口。
- **补交** · 拾取者或审核员可在自己的审核环节提出补充请求，登记具体材料、提请人和环节。每条申请共一次补交机会，进入待补充时按 72 个自然小时计算，申请详情和站内消息显示明确截止日期与时间（北京时间）。剩余 24 小时仍未补交时写入一条站内提醒。截止前成功提交后回原环节，补充请求独立于一次正式审核意见。到点仍待补充则自动驳回，通知双方并释放名额；并发处理只允许一个结果。

### 4.6 UC-22 交接后的冒领举报（v0.2）

- 自交接完成时间起 30 天内，已登录用户可用原招领链接或编号提交冒领举报。第 7 天自动关闭后仍可使用该入口。关闭后的入口只显示定位所需的最少信息。
- 同账号对同一对象最多一次。举报证据、原申请和交接确认记录只有获授权者可查阅。举报独立处理，保留原交接和关闭记录。实体物品争议由招领处线下核查。
- 超出窗口时提示使用经业务方确认的线下咨询渠道。公开视图及举报反馈保护申请人、领取人和保管方的个人信息。

### 4.7 公示截止与已受理申请

- 从首次公示起算 60 个自然日。工作台或补交期间不重算公示期。到期移出公开检索，旧链接显示「公示已结束」，隐藏新申请操作。同一物品事务内检查截止及占位，以服务端接受时间为准，到达截止点时拒绝新申请与重申。
- 无进行中申请且仍处于公示中时，发布转已过期。有进行中申请时相关方继续从「我的申请」或审核待办处理，原补交期限、核验资料与领取操作可用。终审通过仍可交付。到期后申请撤回、被驳回、补交超时或核实未交付而结束时，原结论保留，与释放占位同事务转发布为已过期。已完成交接的发布仍在 7 天后关闭。

### 4.8 超时跟进与值班接手（UC-32）

- 待初审累计 24 小时且仍待初审，发一次站内提醒给拾取者；累计 48 小时且仍待初审，加入「需跟进」。待补充暂停累计，回到初审后继续。终审通过且满 72 小时仍未确认，同样加入领取跟进队列。按申请和节点去重。
- 值班老师为跟进人，按案件授权志愿者查脱敏摘要、催办和记录情况。原初审无法及时取得时，老师说明未取得意见的原因，转入终审并留痕；既有的当事人回避、证据版本校验与唯一占位规则继续适用。接手和原初审同时提交时只允许一次状态迁移。
- 领取待办登记实物仍在、已交付待确认或联系不上。实物仍在由老师核实未交付后结束；已交付提醒领取人补确认；未核实可交下一班或备用老师。本人可在申请详情看当前等待环节和是否已转招领处。演示可预置值班和替补角色，试点排班须由招领处确认（Q-01）。

### 5.1 审核时效统计（Q-07）

1. 用户等待从提交成功算到终审或审核阶段结案，尚未结案时算到观察时点。领取等待单独计时。审核侧用时为待初审与待终审自然小时之和，待补充暂停，转派或老师接手延续原累计时间。
2. 按提交日期分批。24 小时处理率统计审核侧用时不超过 24 小时的正式终审数；48 小时超时率统计终审耗时超过 48 小时及审核累计达 48 小时仍无终审的申请数。分母为同批申请。在相应阈值前因本人撤回或未补交而结案的申请从该指标分母剔除并单列，达到阈值后才结案的仍参与统计。审核侧提前结案仍进分母并单列原因。分母为零显示「暂无样本」。
3. 完整批次分别在期末之后至少 96 小时、120 小时出具 24／48 小时指标。每案补交暂停至多 72 小时，超时任务延迟另行记录。未成熟批次可显示「统计中」和即时待办耗时；已出指标附观察时点，按该时点可复算。
