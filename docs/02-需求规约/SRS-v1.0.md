## 1. 引言

### 1.1 目的

定义校园失物招领与认领审核系统的功能与非功能需求，作为设计、测试与验收的基线。
本文档面向课程评审教师、组内开发与测试成员，以及（可选）保卫处业务方。

### 1.2 范围

本期实现"登录 → 发布 → 检索 → 认领申请 → 双人审核 → 交接核销 → 归档"主链路，
含举报、通知、统计与权限治理。不做范围见 [项目章程](../00-立项/项目章程.md) 第 3 节。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 失物发布 LostItem | 失主发布的"我丢了什么"，用于被检索与被认领 |
| 招领发布 FoundItem | 拾取者发布的"我捡到了什么"，必须携带至少一个核验问题 |
| 核验问题 VerificationQuestion | 招领方预留的、只有真失主能回答的问题（如"卡套颜色"） |
| 认领申请 ClaimApplication | 失主对某条招领提出的所有权主张 |
| 初审 | 由拾取者（发布人）对认领申请给出的建议性结论 |
| 终审 | 由审核员（保卫处）给出的最终结论，通过后生成交接码 |
| 交接码 HandoverToken | 一次性 6 位码，双方在详情页看到同一个码；线下由一方口述、另一方输入即完成交接 |
| 信用分 CreditScore | 账号行为分，初始 100，违规扣减，影响发布与申请权限 |
| 脱敏 | 手机号、证件号在非授权角色视图中替换为 `138****8000` 形式 |
| 遮蔽图 | 图片入库时生成的模糊版本，用于公开列表与详情 |

## 2. 总体描述

### 2.1 用户角色

| 角色 | 说明 | 增量 |
|---|---|---|
| 学生（失主 / 浏览者）`student` | 检索、发布失物、提交认领、举报、接收通知 | v0.1 |
| 拾取者 `finder` | 发布招领、初审认领、登记保管、核销交接码（需认证） | v0.1（认证在 v0.2） |
| 审核员 `reviewer` | 终审、处置举报、审核认证、维护基础数据、看看板 | v0.1 |
| 系统管理员 `admin` | 用户与角色、配置、审计、报表 | v0.2 |
| 定时任务 `system` | 自动过期、超时升级、通知补扫、订阅匹配 | v0.1 |

### 2.2 运行环境

- 浏览器：Chrome / Edge 最近两个大版本；移动端 Safari / 微信内置浏览器
- 服务端：Linux，Python 3.11+
- 数据库：开发 SQLite（FTS5）；部署 PostgreSQL 15+（`tsvector` + GIN）
- 对象存储：开发 MinIO；部署云 OSS

### 2.3 设计与实现约束

| 编号 | 约束 | 来源 |
|---|---|---|
| C-01 | 登录只走学校统一身份认证；演示环境可开本地账号兜底，但必须标记 `auth_source=local` 且生产禁用 | FR-1、R10 |
| C-02 | 手机号、证件号一律在序列化层脱敏，禁止业务代码各自拼接 | FR-3、REQ-N-003 |
| C-03 | 状态迁移只能经 `services` 层，禁止直接 UPDATE 状态字段 | FR-19、REQ-N-002 |
| C-04 | 密钥、token、真实学工号不得进入代码仓库与提示词 | REQ-N-007 |
| C-05 | 认领结论必须由人给出，系统不得自动通过 | FR-16、R1 |
| C-06 | 图片访问一律走预签名 URL，有效期 ≤10 分钟 | FR-6、REQ-N-003 |

| 编号 | 假设 / 依赖 | 不成立时的影响 |

### 4.1 UC-06 发布招领信息并设置核验问题

| 项 | 内容 |
|---|---|
| 参与者 | 拾取者（主）、对象存储（次） |
| 关联需求 | REQ-F-005、REQ-F-006、REQ-F-008 |
| 前置条件 | 已登录且具有 `finder` 角色（v0.1 由管理员在后台直接授予；v0.2 起可自助申请认证，见 UC-02）；信用分 ≥60 |
| 后置条件 | 生成一条状态为「公示中」的招领发布；核验问题答案加密存储 |
| 触发 | 拾取者在"发布招领"页点击提交 |

**主成功场景**

1. 拾取者填写标题、分类、拾取地点、拾取时间、特征描述。
2. 拾取者设置核验问题（1–3 个）与答案，并填写交接地点与保管方式。
3. 拾取者上传图片（0–5 张）。
4. 系统校验必填项；扫描描述中的手机号、证件号与敏感词。
5. 系统对图片压缩并生成遮蔽图，原图存对象存储。
6. 系统对答案做哈希后入库，明文只保留在审核员可见的加密字段。
7. 系统创建发布，状态「公示中」，写状态日志与审计。
8. 系统返回发布详情，并提示"已开始接收认领申请"。

**扩展场景**

- 4a 描述中含 18 位身份证号或 11 位手机号：提交失败，高亮对应字段，提示"请在联系方式字段填写，不要写在描述里"。
- 4b 命中敏感词表：发布状态置「待审核」，提示"内容需人工复核，通常 24 小时内完成"。
- 4c 未设置核验问题：提交失败，提示"招领必须设置至少 1 个核验问题，否则无法判断认领人是否为失主"。
- 5a 图片上传失败或超时：发布仍然成功，图片状态置「待重传」，详情页给出重试入口（REQ-N-006）。
- 前置条件不满足（未认证或信用分 <60）：拒绝发布，提示具体原因与恢复路径（申请认证 / 申诉）。

**业务规则**

| 编号 | 规则 |
|---|---|
| BR-06-1 | 招领必须有 ≥1 个核验问题，答案对失主不可见 |
| BR-06-2 | 拾取者不能在自己的招领下提交认领申请 |
| BR-06-3 | 信用分 <60 不能发布招领（可发布失物） |

**活动图**：`models/sequence/act-uc06-publish-found.puml`

### 4.2 UC-15 提交认领申请

| 项 | 内容 |
|---|---|
| 参与者 | 学生（失主） |
| 关联需求 | REQ-F-013、REQ-F-014 |
| 前置条件 | 已登录；信用分 ≥40；目标招领状态为「公示中」 |
| 后置条件 | 生成一条状态为「待初审」的认领申请；该招领对本人不可再重复申请 |
| 触发 | 失主在招领详情页点击「申请认领」 |

**主成功场景**

1. 失主点击「申请认领」，系统展示招领方设置的核验问题（不展示答案）。
2. 失主填写认领理由、核验答案、可选的补充材料（购买记录截图等）、期望交接时间。
3. 系统校验：目标发布状态、该物品是否已有进行中申请、本人是否已提交过、是否本人发布、信用分阈值。
4. 系统在事务内插入申请（状态「待初审」）；数据库的部分唯一索引保证同一招领同一时刻只有一条进行中申请。
5. 系统写状态日志，向拾取者发"有新认领申请"通知（站内必达）。
6. 系统返回申请详情与后续流程说明。

**扩展场景**

- 3a 目标发布已进入「认领中」或「已交接」：拒绝，提示"该物品已有认领在审核中"。
- 3b 本人已有一条进行中申请：拒绝，返回 409 并给出已有申请的入口。
- 3b1 他人已有一条进行中申请：返回 409 `CLAIM_CONFLICT`，提示"该物品已有认领在审核中，可稍后再试"。
- 3c 目标是本人发布的招领：拒绝（BR-06-2）。
- 3d 信用分 <40：拒绝，提示可申诉恢复。
- 4a 并发提交导致唯一约束冲突：捕获后返回 409，提示"已有申请提交成功"，不产生第二条记录。
- 5a 通知发送失败：不阻塞申请提交，记录投递失败并降级到站内消息。

**活动图**：`models/sequence/act-uc15-submit-claim.puml`

### 4.3 UC-18 审核员终审认领申请

| 项 | 内容 |
|---|---|
| 参与者 | 审核员（主）、对象存储（次，原图） |
| 关联需求 | REQ-F-016、REQ-F-017、REQ-F-019 |
| 前置条件 | 已登录且具备 `claim:review_final` 能力；申请状态为「待终审」；本人不是申请人也不是发布人 |
| 后置条件 | 申请状态落「已通过」并生成交接码，或落「已驳回」；其余进行中申请自动驳回；发布状态相应迁移 |
| 触发 | 审核员在工作台点击某条待终审申请 |

**主成功场景**

1. 审核员打开申请详情：看到招领信息、遮蔽图与原图入口、核验问题与申请人答案、初审意见、申请人历史（申请次数、通过率、信用分）。
2. 审核员选择「通过」，填写审核意见。
3. 系统校验：状态仍为「待终审」（乐观锁 `version`），审核人不是申请人/发布人。
4. 系统在**单个事务**内：申请转「已通过」→ 生成 6 位交接码（哈希存储，72 小时有效）→ 同一发布其余「待初审/待终审」申请转「已驳回（原因：已被他人认领）」→ 发布转「认领中」→ 写状态日志与审计。
5. 系统向申请人、发布人发通知（含交接码与有效期）。
6. 系统返回成功，工作台队列移除该条。

**扩展场景**

- 2a 选择「驳回」：必须选择原因码（核验不符 / 材料不足 / 疑似冒领 / 重复申请），系统置「已驳回」并通知；疑似冒领同时进入举报处置流程候选。
- 2b 选择「要求补充材料」：申请转「待补充」，通知申请人；申请人在 72 小时内可补充一次，超时自动驳回。
- 3a 并发：另一名审核员已处理该申请（`version` 不匹配）：返回 409，提示"该申请已被处理"，刷新队列。
- 3b 审核人越权（是申请人或发布人）：返回 403，且不提示具体原因（避免推测）。
- 4a 交接码生成失败：事务回滚，申请保持「待终审」，返回可重试错误。
- 5a 通知全部失败：不阻塞，交接码可在详情页查看。

**活动图**：`models/sequence/act-uc18-final-review.puml`

### 4.4 UC-19 交接码生成、核销与重发

| 项 | 内容 |
|---|---|
| 参与者 | 拾取者、学生（失主） |
| 关联需求 | REQ-F-017、REQ-F-019 |
| 前置条件 | 申请状态为「已通过」，交接码有效未过期未核销 |
| 后置条件 | 交接码置「已核销」；发布转「已交接」；申请转「已完成」 |
| 触发 | 任一方在"交接"页输入对方出示的码 |

**主成功场景**

1. 双方线下见面，一方从详情页读出交接码。
2. 另一方在「交接」页输入该码，点击「确认交接」。
3. 系统校验：码存在、未过期、未核销、调用者是该申请的两方之一。
4. 系统在事务内：交接码置「已核销」并记录核销人与时间 → 申请转「已完成」→ 发布转「已交接」→ 写状态日志。
5. 系统通知双方"交接完成"，并提示可对本次经历做评价（v0.3）。
6. 发布在 7 天后自动转「已关闭」。

**扩展场景**

- 3a 码已过期：返回 410，提示"交接码已过期，可申请重发（剩余次数 N）"。
- 3b 码已被核销：返回 409，展示核销时间，避免重复交接。
- 3c 调用者不是该申请的两方：返回 403，不泄露码是否存在。
- 3d 连续 5 次输错：该申请锁定 30 分钟，写审计。
- 重发：发布人或申请人可申请重发，最多 2 次，每次生成新码并作废旧码。
