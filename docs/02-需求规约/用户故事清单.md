## 2. 使用约定

| 项 | 规则 |
|---|---|
| 故事格式 | 作为〈角色〉，我想要〈能力〉，以便〈价值〉；价值必须写"业务后果"，不写"方便管理" |
| 角色口径 | 与 SRS §2.1 一致：`student`／`finder`／`reviewer`／`admin`／`system`；同一账号可叠加 `student` + `finder` |
| 验收标准格式 | 统一 Given（前提）／When（动作）／Then（可观察结果），Then 必须能被一条自动化测试直接断言 |
| 完成定义（DoD） | ① AC 全部有对应 TC；② 越权与边界场景有 TC；③ 状态迁移写日志；④ 敏感字段走脱敏层；⑤ 关联 REQ 与 UC 已登记追溯矩阵 |
| 状态取值 | `已细化`（有 AC）／`待细化`（已登记，未写 AC）／`待拆`（>1 人日，需拆分）／`阻塞`（依赖外部，如 A-01 认证） |
| 估算单位 | 理想人日（1 人日 = 6 小时有效编码 + 自测）；未估算的写"—" |
| 编号稳定性 | 故事编号一经分配不复用；删除的故事标 `作废` 并保留行，避免 TC 引用断链 |
| 不写什么 | 不写技术方案（那是设计文档的事）；不写"系统应该……"（那是需求的事）；故事只描述**谁要什么价值** |
