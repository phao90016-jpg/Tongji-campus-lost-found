# 评审单（模板）

> 负责人：评审组织人（兼 AI 使用负责人，成员待填）｜状态：模板，复制后另存为 `评审单-<被评对象>-<版本>.md`
> 使用方式：**一次评审一张单**。复制本文件 → 改标题与基本信息 → 逐条填检查项 → 缺陷清单必须写满（不允许只写"都同意"）→ 结论勾选 → 签字 → 把结论回填到被评文档的"评审记录"节。
> 纪律：**没有缺陷清单的评审单视为未评审**。一条缺陷都没提的评审，通常意味着没看懂。

| 项 | 内容 |
|---|---|
| 评审单编号 | RV-〔年〕-〔序号〕，如 RV-2025-03 |

| 版本 / 提交 | 〔v1.0 / commit sha〕 |
| 评审类型 | 文档评审 / 设计评审 / 代码评审 / 里程碑放行评审 |
| 评审方式 | 会议评审 / 走查（walkthrough） / 桌面检查 |
| 评审日期 | 〔待填〕 |
| 会议时长 | 〔待填〕分钟 |
| 组织人 | 〔待填〕 |
| 记录人 | 〔待填〕（组织人与记录人不得为同一人） |
| 依据 | 课程要求、[项目章程](../00-立项/项目章程.md)、上游文档、检查表 |
| 结论 | 通过 / 修改后通过 / 不通过（见 §5） |

## 2. 参与人

| 姓名 | 角色 | 评审视角 | 是否提交书面意见 | 是否需回避 |
|---|---|---|---|---|
| 待填 | 项目经理 | 计划、范围、风险 | 是 / 否 | 否 |
| 待填 | 需求分析师 | 需求完整性与可验证性 | 是 / 否 | 被评文档作者需回避表决 |
| 待填 | 架构 / 设计工程师 | 可实现性与一致性 | 是 / 否 | 否 |
| 待填 | 开发工程师 | 落地成本与歧义 | 是 / 否 | 否 |
| 待填 | 测试 / 质量工程师 | 可测性、验收口径 | 是 / 否 | 否 |
| 待填 | 评审组织人（兼 AI 使用负责人） | 流程、留痕、AI 产出核查 | 是 / 否 | 否 |

> **回避规则**：被评文档的作者不参与"是否通过"的表决，但必须到场答疑并承担缺陷修改责任。
> **法定人数**：至少 4 人到场，其中至少 1 人不是本文档作者。

## 3. 检查项

> 判定取值：**通过 / 部分通过 / 不通过 / 不适用**。任一项"不通过"即不得判"通过"。
> 每条检查项必须写"证据位置"（章节号、行号、文件路径），不接受"感觉没问题"。

| 编号 | 检查项 | 判定标准 | 判定 | 证据位置 / 说明 |
|---|---|---|---|---|
| CK-01 | 完整性 | 该阶段要求的章节/条目齐全，无"待填"残留（除明确标注的占位项） | 通过 / 部分通过 / 不通过 / 不适用 | |
| CK-02 | 编号与术语一致 | 编号规则统一（REQ-/UC-/ADR-/R-…），术语与术语表一致，跨文档同一对象只有一个叫法 | | |
| CK-03 | 可验证性 | 每条需求/设计条目都有可执行的验收方式或测试断言，不出现"良好""尽量""合理"等不可判定表述 | | |
| CK-04 | 可追溯 | 需求 ↔ 用例 ↔ 设计 ↔ 测试 双向可追，无孤儿条目、无悬空引用 | | |
| CK-05 | 边界与异常 | 主成功场景之外，异常/并发/超时/权限不足等分支有明确处理与返回码 | | |
| CK-06 | 非功能覆盖 | 性能、并发、安全、可靠性、合规各有指标、口径与验收方式，且口径唯一 | | |
| CK-07 | 约束与假设 | 设计与实现约束、外部依赖假设、不成立时的影响均已写明 | | |
| CK-08 | AI 产出核查 | 由 AI 起草的内容已在 [AI 使用台账](../08-AI使用/AI使用台账.md) 登记，且"人把关方式"可复现 | | |

## 4. 缺陷清单

> **不允许只写"都同意"**。本表是评审单的核心，空表即评审无效。
> 严重程度：**高**＝会导致返工或验收失败；**中**＝影响理解与维护；**低**＝文字与格式。

## 5. 结论

- [ ] **通过**：无高严重度缺陷，中低缺陷可带入下一阶段跟踪
- [ ] **修改后通过**：存在高严重度缺陷或 ≥3 条中严重度缺陷，修改并复核后视为通过，不另开会
- [ ] **不通过**：存在结构性缺陷（章节缺失、口径冲突、无法验收），需重写后重新评审
