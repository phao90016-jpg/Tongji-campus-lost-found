# 竞品分析：校园失物招领的 6 个真实渠道

> 对应单元：2 需求调研与规约｜检查点：第 3 次课（M2 需求基线，作为调研报告的桌面研究部分）
> 负责人：需求分析师｜状态：草稿，待评审；功能判定以公开可见页面与本人使用经验为准，**未做用户量统计与逆向分析**
> 依据：[选题文稿](../00-立项/选题文稿.md) 第一节问题定义、[调研计划表](调研计划表.md) §4 M-05

## 1. 结论（先看这里）

| 编号 | 结论 | 依据 |
|---|---|---|
| **K-1** | **"信息聚合"这一层已经被解决得很好了**——群、校园墙、BBS、小程序都能让人"看见"。再做一个"能发能搜"的失物招领，只是第七个渠道。 | 对比表 A1–A6 列：6 个对象中 5 个具备发布能力，4 个具备检索或可检索的历史记录 |
| **K-2** | **"认领可核验"这一层，6 个对象里没有一个真正做**——全部止步于"私聊自述"或"线下口头问答"。这是本项目的唯一切入点。 | 对比表 B1–B4 行：核验问题 0/6、双人审核 0/6、交接凭证 0/6、认领留痕 1/6（仅登记簿有纸质签字） |
| **K-3** | **权威与效率是分裂的**：保卫处有权威（登记簿、可保管实物）但没有线上效率与触达；线上渠道有效率（即时、覆盖广）但没有权威、没有责任人、没有留痕。本项目的机会是把两者接起来，而不是取代任何一方。 | 对比表 C1–C4 行：登记簿"权威✓／触达✗／检索✗"；群与校园墙"触达✓／权威✗／留痕✗" |
| **K-4** | 竞品普遍**不采集、不脱敏、不留痕**，因为它们的商业模式与合规责任都不在这里。这既是本项目的差异化空间，也是必须自己承担的成本（R2、REQ-N-003）。 | 对比表 D1–D4 行：隐私脱敏 0/6、审计 0/6、信用与处置 0/6 |

> 一句话定位：**别人做"失物信息广场"，我们做"认领的核验与交接"**。广场是入口，核验才是产品。

## 2. 分析对象（6 个真实存在的渠道／产品）

| 编号 | 对象 | 形态 | 谁在用 | 与本项目的关系 | 信息获取方式 |
|---|---|---|---|---|---|
| **C1** | 班级群／年级群／社团群（微信群、QQ 群） | 即时通讯群聊 | 学生、辅导员 | 最主要的现状替代方案 | 本人所在群的实际使用经验 + 公开可见的群公告习惯 |
| **C2** | 校园墙（QQ 空间墙、微信"万能墙／表白墙"类账号） | 自媒体账号 + 私信投稿 | 全校学生 | 覆盖最广的信息渠道 | 公开可见的墙号内容（失物招领类投稿） |
| **C3** | 保卫处／失物招领处登记簿（线下台账 + 窗口） | 纸质台账 + 人工窗口 | 保卫处、失主、拾取者 | 唯一的"权威"渠道，也是终审方的现状工具 | 公开的失物招领流程告示；具体字段需 S3 访谈确认（**待补充**） |
| **C4** | 闲鱼"失物招领"入口／转转同类板块 | 二手交易平台内的失物分区 | 社会公众、部分学生 | 跨校、跨社会的通用方案，可对照"平台怎么做核验" | 公开 App 页面与帮助文档 |
| **C5** | 高校 BBS 失物招领版（如未名 BBS `LostAndFound` 版、水木社区失物招领版） | 论坛版面 | 校内师生、校友 | 最"结构化"的传统方案（版规、置顶、模板） | 公开可访问的版面与版规 |
| **C6** | 学校自建失物招领小程序／公众号（以常见"XX 大学失物招领"类小程序为代表） | 小程序／公众号 | 校内学生 | 最接近本项目的形态，重点对照其审核深度 | 公开的小程序介绍页与使用截图（具体校名与版本**待补充**） |

**选取理由**：C1–C3 覆盖"学生自发 + 权威线下"两个极端；C4–C5 提供"平台化"与"论坛化"两种成熟范式；C6 是最直接的同类系统。六个对象足以覆盖"发布—检索—认领—交接—追责"全链路的现有解法。

## 4. 关键差距解读（为什么这些格子空着）

| 差距 | 竞品为什么不做／做不到 | 对本项目的含义 |
|---|---|---|
| **核验问题（B1）** | 群与墙是通用沟通工具，没有"物品"这个概念，无法承载物品级字段；平台类产品（C4）做失物只是导流，不承担核验责任 | 这是**产品定位级**空白，不是功能遗漏。做它需要"物品—发布—申请"的数据结构，本项目 SRS 的 AC-08/AC-09/AC-13/AC-14 正是为此设计 |
| **双人审核（B3）** | 需要"有人愿意当审核方"。群主、墙主、版主都没有这个职责；平台没有线下实体可交接；只有保卫处有职责，但没有工具 | 双人审核的可行性**取决于 S3 保卫处是否愿意承担终审**（假设 A-02）。这也是本项目最大的人力风险（R9） |
| **交接凭证（B4）** | 线上平台无法验证线下是否真的交接了；群聊根本没有"完成"这个概念 | 交接码把"线上结论"与"线下事实"绑定，是本项目相对所有竞品的结构性差异（REQ-F-017） |
| **多人争抢互斥（B6）** | 群聊里"谁先私聊谁得"是默认规则，没人有仲裁权；平台不涉及实物归属 | 需要状态机 + 唯一约束（REQ-F-019、REQ-N-002、ADR-0002），这是纯工程问题，也是可测试点 |
| **隐私遮蔽（D2）** | 通用渠道没有识别证件的能力与动机；平台有动力但失物不是主业 | 图片入库即遮蔽（REQ-F-006）必须自己做，且必须承认 v0.1 只能"整图轻度模糊 + 审核员看原图" |
| **信用与处置（C4）** | 群／墙／BBS 的惩罚手段是踢人删帖，无法跨渠道生效；平台信用不覆盖校园身份 | 信用分必须挂在**实名校验过的账号**上（REQ-F-001、REQ-F-021），这也是"必须走统一认证"的产品理由 |

## 5. 差异化机会（3 条，全部指向"认领可核验"）

### O-1 把"证明是我的"从自述变成**可回答、可留痕的问题**

| 项 | 内容 |
|---|---|
| 机会描述 | 招领发布时强制设置 1–3 个核验问题（"耳机盒内侧贴了什么"），答案对失主不可见；认领时必须作答，答案进入审核页而非聊天窗口 |
| 竞品缺口 | 对比表 B1 行 6/6 为 ✗；B2 行仅登记簿"部分" |
| 落点需求 | [REQ-F-005](../02-需求规约/SRS-v1.0.md)（发布招领必须设核验问题）、REQ-F-013（认领须作答）、REQ-F-015（初审可见答案） |
| 对应用例 | UC-06、UC-15、UC-17 |
| 可测锚点 | TC-UC06-02（未设问题不能发布）、TC-UC15-02（答案错误不直接拒绝，转人工） |
| 不做什么 | 不做"AI 判断答案对不对"——答案对错由人判（C-05、R1） |

### O-2 把"敢不敢给"变成**双人把关 + 一次性交接码**

| 项 | 内容 |
|---|---|
| 机会描述 | 拾取者初审（建议通过／拒绝／补充提问）→ 保卫处终审（通过／驳回／补充材料）→ 通过才生成 6 位一次性交接码，线下凭码核销，状态才落"已交接" |
| 竞品缺口 | 对比表 B3 行 6/6 为 ✗；B4 行 5/6 为 ✗；B7 行仅 2 个"部分" |
| 落点需求 | REQ-F-015、REQ-F-016、REQ-F-017、REQ-F-019 |
| 对应用例 | UC-17、UC-18、UC-19 |
| 可测锚点 | TC-UC18-02（终审通过时其余申请自动驳回）、TC-UC18-03（并发终审 409）、TC-UC19-01（交接码一次性） |
| 为什么不重 | 双人审核把责任分摊给"最了解物品的人"（拾取者）与"有权威的人"（保卫处）；交接码把线上结论锚到线下事实。这两件事竞品都没做，因为它们没有"线下实体交接点" |

### O-3 让恶意行为**有代价、有记录、可申诉**

| 项 | 内容 |
|---|---|
| 机会描述 | 举报（虚假信息／冒领／骚扰／违禁品／重复发布）+ 处置（警告／下架／封禁）+ 信用分（初始 100，冒领 −40）+ 申诉（非原处置人复核）+ 审计留痕 |
| 竞品缺口 | 对比表 C2、C4 行：处置能力集中在平台类产品，校园渠道只有"踢人删帖"；C5 行审计"部分"；D2 行隐私 0/6 |
| 落点需求 | REQ-F-020、REQ-F-021、REQ-F-022、REQ-F-026、REQ-N-003 |
| 对应用例 | UC-22、UC-23、UC-24、UC-25、UC-33、UC-35 |
| 可测锚点 | TC-UC22-02（同一对象重复举报 409）、TC-UC24-01（信用分扣减与发布限制）、TC-NFR02-01（脱敏） |
| 诚实边界 | 信用分不能真的"防住"冒领，只能提高成本；因此结论必须人工签字（C-05），不能把风控外包给分数 |

## 6. 抄什么、不抄什么

| 竞品的做法 | 抄／不抄 | 理由 |
|---|---|---|
| 校园墙的"投稿 + 审核后发布"（C2） | **抄**（降级为"敏感词命中转人工"） | 成本低、能挡住明显违规；但全量人工审不现实（REQ-F-008 只做命中转审） |
| BBS 的版规与模板化发帖（C5） | **抄** | 结构化字段比自由文本可检索，直接体现在 REQ-F-004/005 的必填项上 |
| 登记簿的"认领人签字"（C3） | **抄**（升级为电子留痕） | 签字的价值是"事后可追"，用审核记录 + 审计日志替代（AC-15、AC-26） |
| 闲鱼的"确认收货"式凭证（C4） | **抄**（改造为交接码） | 凭证要能证明"东西真的给了"，且必须一次性、可过期 |
| 闲鱼的交易评价体系（C4） | **不抄** | 失物不是交易，评价会诱导"为了好评赶紧给"，与核验目标冲突 |
| 群聊的即时性（C1） | **部分抄** | 用通知 + 站内消息替代，但明确"通知是尽力而为"，不能当作用户已知情（R4） |
| 平台的实名 + 信用分（C4） | **抄**（挂到校园统一认证上） | 没有实名，信用分无意义（CR-001） |
| 小程序常见的"一键拨号联系失主" | **不抄** | 直接暴露联系方式，正是 P-05 痛点的来源（REQ-F-003） |
| 站内即时聊天 | **不抄** | 已在 CR-002 中删除，改为交接码 + 审核员可见联系方式 |

## 7. 结论与风险

| 项 | 内容 |
|---|---|
| **定位结论** | 本项目不与任何竞品在"发布与检索"上竞争，而是把竞品的终点（"你私聊他吧"）当作自己的起点（"提交申请，走审核"）。 |
| **可验证的差异化** | 三条机会都能落到具体 REQ 与 TC，且都能在 v0.1 演示（发布招领设问题 → 提交认领 → 初审 → 终审 → 交接码核销）。 |
| **最大不确定性** | 双人审核依赖保卫处愿意承担终审（A-02、R9）。若 S3 访谈证明"没人愿意审"，则 O-2 需降级为"拾取者初审 + 系统留痕"，并走[变更记录](../02-需求规约/变更记录.md)。 |
| **第二不确定性** | 交接码要求双方都在系统内操作；若现实中大量交接发生在"一方没带手机"的场景，需保留"审核员代核销"的后备路径（当前 SRS 未定义，列为待决）。 |
| **不宣称的事** | 不宣称竞品"做得差"——它们在各自目标上做得够好；本项目只是把目标换成了"核验与交接"。 |
