> 负责人：AI 使用负责人（成员待填）｜状态：持续更新，每次课末登记，第 8 次课归档进 [AI 使用报告](AI使用报告.md)

> 登记范围：由 AI 起草、改写、生成的一切产出——需求条目、设计片段、代码、测试、图表、讲稿、文档排版。
> 不登记：仅改错别字、调标点这类不改变语义的用途（仍建议顺手记一行，便于复盘）。

## 4. 人守关卡记录（3 个案例）

三个案例都取自真实返工：AI 产出看起来能用、跑得通，但**在评审或验证中被人的一条具体检查打回**。
每个案例都引出一个 ADR 或一条设计约定，这是本项目"人在关卡上"最硬的证据。

### 案例 1：终审事务漏了"驳回其余申请"（引出 ADR-0002）

| 项 | 内容 |
|---|---|
| 场景 | 第 13 周实现构件 2「终审事务」（[详细设计](../04-设计/详细设计.md) 构件 2，DES-API-005）。提示词里给了 SRS §4.3 UC-18 的主成功场景与 `claim_application`、`handover_token` 两张表结构，要求"通过时在一个事务里完成"。 |
| AI 产出 | `final_review()` 约 60 行：`BEGIN` → 校验 `version` 乐观锁 → 申请置 `approved` → 生成 6 位码入库 → `item` 置 `claiming` → 写状态日志。单人认领的 happy path 一次跑通，`TC-UC18-01` 通过。 |
| 发现的问题 | ① 漏了"同物品其余进行中申请置 `rejected`"这条 `UPDATE`，与 UC-18 后置条件"其余进行中申请自动驳回"直接不符；② 更要紧的是 AI 没有意识到 `uq_claim_active` 是**部分唯一索引且包含 `approved`**——不驳回其余申请，`approved` 的占位就一直占着，其余申请会永久卡在 `pending_final`，审核员工作台里出现"同一物品两条待终审"，R3 从"两人都被通过"退化成"两人都在等"，用户体验更差且更难排查；③ AI 自己写的单测只断言了 happy path，没有"其余申请"这条断言。 |
| 人的处理 | 测试 / 质量按 [SRS](../02-需求规约/SRS-v1.0.md) 的用例后置条件逐条比对，跑 `TC-UC18-02`（通过后其余申请应为 `rejected`）失败；开发补事务内 `UPDATE ... WHERE item_id=? AND id<>? AND status IN ('pending_first','pending_final','need_more')`，并把断言写进单测；架构 / 设计据此写 [ADR-0002](../04-设计/adr/0002-认领并发控制.md)，把"驳回其余申请必须在同一事务"和"部分唯一索引必须包含 `approved`"写成决策与负面后果。 |
| 结论 | AI 产出弃用重写（AI-012）。关卡动作 = **逐条比对用例后置条件 + 单测断言**。教训：AI 能写出"能跑的代码"，但不会主动把业务规则翻译成约束；约束必须由人从需求文档里搬过来。 |

### 案例 2：脱敏只做在前端，抓包即泄露（引出 ADR-0003）

| 项 | 内容 |
|---|---|
| 场景 | 第 14 周做构件 4「脱敏、字段可见性与审计」（DES-SVC-002 / DES-SEC-002）。提示词原话："写一个把手机号打星号的工具函数，列表页和详情页都要用。" |
| AI 产出 | 前端 `formatPhone(v)`：`v.slice(0,3) + '****' + v.slice(-4)`；后端接口照常返回 `applicant.phone` 原文；AI 还在注释里"贴心地"写了一句"展示时脱敏即可，后端保持原文便于调试"。 |
| 发现的问题 | 浏览器 DevTools → Network 看 `GET /api/claims/{id}`，响应体里 `applicant.phone` 是完整 11 位；换学生 B 的账号 `curl` 同一个接口，同样拿到 A 的原文。即"前端脱敏 = 抓包即泄露"，与 REQ-N-003、约束 C-02（"一律在序列化层脱敏，禁止业务代码各自拼接"）直接冲突，R2 命中。若按此交付，期末演示时随便一个同学打开 F12 就能看到全场手机号。 |
| 人的处理 | 删掉前端脱敏函数，改为 `services/visibility.py` 统一出口：`visible_fields(viewer, obj)` + `mask_phone()`，按 `pii:read` 能力 + 关系（本人 / 已通过终审的对方）判定；补一条单测"响应 JSON 用正则 `\d{11}` 全文扫描必须为 0 命中"；审核员读明文必须写 `pii.read` 审计。据此写 [ADR-0003](../04-设计/adr/0003-敏感信息分级与脱敏.md)，把"前端脱敏"明确列为**否决方案**并附抓包证据。 |
| 结论 | 部分采纳（保留 `mask_phone` 实现，改掉调用位置）。关卡动作 = **抓包 + 正则断言**。教训：AI 会选"改动最小"的方案，而安全边界恰恰要求"改动在正确的那一层"；这种判断不能外包。 |

### 案例 3：交接码 4 位数字 + 明文入库（引出构件 3 的安全清单）

| 项 | 内容 |
|---|---|
| 场景 | 第 14 周做构件 3「交接码」（DES-SVC-003）。提示词只说了"生成一个交接码，双方输入后核销，核销完物品状态改为已交接"。 |
| AI 产出 | `code = str(random.randint(1000, 9999))`；`handover_token.code` 直接存 4 位明文；核销用 `WHERE code = ?`；没有有效期字段、没有重发、没有输错计数、没有和 `claim_id` 绑定。 |
| 发现的问题 | ① 码空间只有 10⁴，配合"5 次输错锁定"也能在多个申请之间轮换试探；② 明文入库，数据库被拖走即可直接冒领，R1 直接命中；③ 没有 72 小时有效期与"重发 ≤2 次"，与 REQ-F-017 不符；④ 没有绑定 `claim_id`，一个码可能命中别人的申请；⑤ `random` 不是密码学安全的随机源。 |
| 人的处理 | 改为 6 位、去混淆字母表（去掉 `0/O`、`1/I`、`B`、`Z` 六个易混字符，保留 `8` 与 `2`）、`secrets.choice`、只存 `sha256(code + claim_id)`、72 小时有效、重发 ≤2 次且旧码立即作废、5 次输错锁 30 分钟、核销用 `WHERE consumed_at IS NULL` 保证幂等。复核时还顺手数了一遍字母表：实际 **30 个字符**，`30⁶ ≈ 7.29 亿`，与详细设计里"31 个字符 / 约 8.9 亿"的注释对不上（见 §7 待修项）。 |
| 结论 | AI 产出弃用重写（AI-016）。关卡动作 = **安全清单逐条打勾**（长度 / 存储形式 / 有效期 / 重发 / 锁定 / 绑定 / 幂等 / 随机源）。教训：提示词越短，AI 越会给出"能演示"的最简实现；安全相关的构件必须给足约束，否则就是在赌。 |

### 三案例对照

| 案例 | 发现时点 | 发现方式 | 若未发现的后果 | 留痕 |
|---|---|---|---|---|
| 1 终审事务 | 编码后评审 | 用例后置条件逐条比对 + 单测断言 | 同一物品出现两条待终审，认领永久卡死 | ADR-0002、AI-012、TC-UC18-02 |
| 2 前端脱敏 | 编码后验证 | DevTools 抓包 + 换账号 `curl` | 全场手机号可被 F12 读取，R2 成为既成事实 | ADR-0003、AI-014、TC-NFR02-01 |
| 3 交接码 | 编码后复核 | 安全清单逐条打勾 | 4 位明文码可被试探与拖库利用，R1 命中 | 详细设计构件 3、AI-016、TC-UC19-02 |

> 三个案例的共同点：**AI 的产出都能跑**，错的是"没有把需求里的约束搬进实现"。所以本项目的关卡不是"看代码像不像"，而是"拿需求条目和风险条目去对"。

## 5. 各阶段 AI 参与比例估计

> 分母是该阶段的"交付条目"（需求条目、设计构件、接口、测试用例、文档章节），不是工时。

| 阶段 | AI 参与比例（估计） | 主要用途 | 人的把关方式 | 估计依据 |
|---|---|---|---|---|
| 立项与选型 | 10%–20% | 范围清单草稿、风险表述润色、同类系统对照 | 逐条可行性反问；范围取舍由项目经理签字 | 选题文稿的"明确不做"与选型论证均为人写，AI 只给候选 |
| 需求调研 | 15%–25% | 访谈提纲、场景复述、竞品功能对照 | 来源可核实性逐条检查，不可核实的删 | 访谈记录与场景细节由人补 |
| 需求规约 | 25%–35% | REQ 条目表格化、验收方式措辞、覆盖自查 | 逐条映射选题文稿；口径由人定义；评审单留缺陷 | 27 条 FR 的"需求"文字多为 AI 起草后改，判定逻辑由人定 |
| 需求建模 | 20%–30% | PlantUML 骨架、状态迁移表初稿、CRC 卡字段 | 与用例逐条比对；删掉 AI 自行发明的用例 | 图形布局与关系由人重排 |
| 概要 / 详细设计 | 30%–40% | 构件骨架、异常与降级表、备选方案对比 | ADR 由人签字；并发与安全方案由人定 | 6 个构件的算法骨架 AI 起草比例高，约束由人补 |
| 编码 | 35%–50% | 样板代码、序列化、路由、测试脚手架 | 代码评审 + CI + 单测断言；三处人签字 | 业务规则分支基本由人写或重写（见 §4） |
| 测试 | 20%–30% | 用例骨架、并发脚本思路、断言模板 | 人工改为真实 HTTP 并发；断言由人定阈值 | 测试数据与判定口径由人设计 |
| 文档排版与交叉引用 | 50%–70% | 表格转写、链接检查、术语统一 | 人工确认悬空引用与编号 | 排版类工作 AI 产出保留率最高 |
| 评审组织 | 5%–10% | 检查项裁剪、缺陷候选 | 逐条回原文核对，删误报补漏报 | 缺陷定级与结论由人给 |
| 课堂讲解准备 | 20%–30% | 讲稿骨架、问答预演 | 人工补真实数据与追问准备 | 讲稿的"讲什么"由人定 |

**一句话读法**：越靠近"判断"的环节（需求确认、并发正确性、安全边界、评审结论），AI 参与比例越低；越靠近"形式"的环节（排版、样板代码、表格），比例越高。这个分布本身就是结论。
