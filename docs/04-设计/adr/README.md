# 架构决策记录（ADR）

每做一次影响架构的选择，写一份 ADR。编号连续，不复用。

## 何时必须写 ADR

- 架构风格、分层方式、模块边界
- 关键技术选型（数据库、并发控制、认证方案、存储）
- 接口契约的重大变更
- 为规避某个风险而做的设计取舍

## 模板

```markdown
# ADR-000N 标题

- **状态**：提议 / 已接受 / 已废弃 / 被 ADR-000M 取代
- **日期**：
- **决策人**：（架构决策须人签字）

## 背景
## 决策
## 备选方案（表格：方案 / 优点 / 缺点 / 结论）
## 后果（正面 / 负面）
## 关联（需求、风险、设计文档、测试）
```

## 写作要求

| 要求 | 理由 |
|---|---|
| 必须写"备选方案"并给出否决理由 | 只写"我们选了 A"无法体现设计判断，评审会追问 |
| 必须写"负面后果" | 没有负面后果的方案通常是想得不够深 |
| 必须链到需求编号与风险编号 | 与追溯矩阵一致，避免 ADR 变成孤立文档 |
| 状态变更要留痕 | 被取代的 ADR 保留原文，状态改为"被 ADR-000M 取代" |
