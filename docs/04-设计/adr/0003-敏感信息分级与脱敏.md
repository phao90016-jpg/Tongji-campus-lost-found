# ADR-0003 敏感信息分级与统一脱敏

- **状态**：已接受
- **日期**：待填
- **决策人**：架构 / 设计工程师 + 项目经理（涉及合规，须双签）

## 背景

失物招领天然要处理两类敏感信息：

1. **联系方式**（手机号、微信号）——不给人，失主与拾取者联系不上；给了所有人，会被骚扰与爬取。
2. **证件类图片**（校园卡、身份证、快递面单）——图片里往往直接印着姓名、学号、身份证号。

立项调研时统计过：提交上来的证件类照片中，正反面齐全、信息可读的占多数；用户不会主动打码。
风险登记册 R2 把"敏感信息泄露"列为本项目三大重点风险之一。

## 决策

采用**字段级分级 + 序列化层统一脱敏 + 图片入库遮蔽 + 短期预签名 URL** 四层组合：

| 层 | 做法 |
|---|---|
| 数据分级 | 手机号、微信号、证件号标 `pii`；物品描述标 `public`；核验答案标 `secret` |
| 脱敏位置 | 统一在 `services/visibility.py` 的序列化函数里做，业务代码不得自行拼接 |
| 可见性判定 | 本人资料页可读本人号码；他人原文需老师具备 `pii:read` 并有案件授权，访问留痕。领取安排只返回服务点公用联系渠道（CR-006） |
| 图片 | 入库生成遮蔽图；公开视图只返回遮蔽图；原图 URL 由 HMAC 签名 + 10 分钟过期 |
| 审计 | 每次明文读取、原图读取写 `audit_log`（只记元数据） |

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 不脱敏，靠用户自律 | 实现零成本 | 等于把责任推给用户；R2 必然发生 | 否决 |
| 前端脱敏（接口返回原文，前端打星号） | 前端简单 | 抓包即泄露，等于没做 | 否决 |
| 各接口自己拼接脱敏 | 灵活 | 早晚漏一个；无法统一审计 | 否决 |
| **序列化层统一脱敏 + 能力判定** | 一处实现、可单测、可审计 | 需要设计好视图模型 | **采纳** |
| 全字段加密存储 | 更安全 | 检索、排序、统计都要解密，复杂度陡增；课程规模不值得 | 部分采纳（核验答案加密） |

## 后果

**正面**

- 一条断言就能守住底线：普通详情、领取卡和通知里不出现测试账户的私人号码
- 越权与脱敏共用同一套判定，减少"两个地方判断不一致"的漏洞
- 审计可回答"谁在什么时候看了谁的手机号"

**负面**

- 序列化层多一层映射，字段增减要同步改视图模型（用测试兜住）
- 审核员看到的原文依赖 `pii:read` 能力，能力配错会直接影响业务（用集成测试覆盖）
- 整图模糊会让特征看不清，需在审核页提供原图（因此原图访问必须审计）
