# ADR-0002 用"部分唯一索引 + 乐观锁"保证同一物品只有一条进行中申请

- **状态**：已接受
- **日期**：待填
- **决策人**：架构 / 设计工程师

## 背景

同一招领可能被多人同时提交认领。当前业务只允许一条进行中申请，待初审、待终审、待补充和已通过待领取均占位。仅使用应用层先查后插，会让两个请求在并发时都通过检查。

## 决策

用数据库部分唯一索引约束占位，用状态和版本比较处理同一申请的审核、撤回、补交、超时和领取确认竞态。

```sql
CREATE UNIQUE INDEX uq_claim_active ON claim_application(item_id)
  WHERE status IN ('pending_first','pending_final','need_more','approved');
```

- 已有进行中记录时，后到提交返回 409，保持旧申请不变。
- 终审仅迁移当前申请。通过保留占位；驳回、撤回、补交超时驳回、确认交接或核实未交付后结束才释放占位。
- 同一物品内串行校验申请资格和证据版本。首次撤回后至多关联一次重申，历史记录保留。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 应用层先查后插 | 简单 | 并发下双写，R3 必然发生 | 否决 |
| 数据库唯一索引（无 WHERE） | 强约束 | 物品一旦被认领就永远不能再有申请（历史记录也被禁） | 否决 |
| **部分唯一索引 + 乐观锁** | 只约束"进行中"，历史保留；数据库保证并发安全 | SQLite/PostgreSQL 都支持，须验证事务和索引行为 | **采纳** |
| 分布式锁（Redis） | 通用 | 引入额外组件，单实例部署不需要 | 否决 |
| 串行化事务（`SERIALIZABLE`） | 语义强 | SQLite 不支持真串行化隔离级别；PostgreSQL 下性能与死锁成本高 | 否决 |

## 后果

**正面**

- 并发安全由数据库保证，不依赖代码正确性；测试可断言"10 并发只成功 1 条"
- 历史申请（已驳回/已撤回）不受影响，可保留完整的竞争记录用于统计
- 审批状态与提交冲突在各自发生的节点处理，能明确告知申请人当前进度

**负面**

- 需要理解部分索引：`approved` 必须包含在索引条件里，否则终审通过后唯一索引释放，
  又会有新申请进来（业务上不希望——物品已经在交接流程中）
- SQLite 的部分索引在旧版本（<3.8）不支持；本项目要求 3.24+，已在 `probe/` 中验证
- `need_more` 也算"进行中"，语义上正确但评审时需要解释清楚
