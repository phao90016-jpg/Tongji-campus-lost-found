# ADR-0002 用"部分唯一索引 + 乐观锁"保证同一物品只有一条进行中申请

- **状态**：已接受
- **日期**：待填
- **决策人**：架构 / 设计工程师

## 背景

一条招领可能同时收到多条认领申请（真实场景里常见：群里一转发，五个人来认领）。业务规则是：

1. 同一用户对同一物品只能有 1 条进行中申请；
2. 同一物品在同一时刻只能有 1 条进行中申请——否则终审通过时会出现"两个人都被通过"；
3. 终审通过时必须原子地驳回其余申请。

规则 2 是核心。若只在应用层用 `SELECT ... WHERE status IN (...) THEN INSERT` 判断，
在并发下会双写成功（两个请求都查到"没有进行中申请"）。这是 R3 风险。

## 决策

用**数据库的部分唯一索引**保证规则 2，用**乐观锁**保证规则 3：

```sql
CREATE UNIQUE INDEX uq_claim_active ON claim_application(item_id)
  WHERE status IN ('pending_first','pending_final','need_more','approved');
```

- 插入申请时若已有进行中记录 → `IntegrityError` → 映射 409 `CLAIM_CONFLICT`
- 终审 `UPDATE claim_application SET status=... WHERE id=? AND version=? AND status='pending_final'`
  → `rowcount=0` 说明已被处理 → 409
- 终审通过后在同一事务内把同物品其余进行中申请置 `rejected`，释放唯一索引占位

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 应用层先查后插 | 简单 | 并发下双写，R3 必然发生 | 否决 |
| 数据库唯一索引（无 WHERE） | 强约束 | 物品一旦被认领就永远不能再有申请（历史记录也被禁） | 否决 |
| **部分唯一索引 + 乐观锁** | 只约束"进行中"，历史保留；数据库保证并发安全 | SQLite/PostgreSQL 都支持，但需要理解部分索引语义 | **采纳** |
| 分布式锁（Redis） | 通用 | 引入额外组件，单实例部署不需要 | 否决 |
| 串行化事务（`SERIALIZABLE`） | 语义强 | SQLite 不支持真串行化隔离级别；PostgreSQL 下性能与死锁成本高 | 否决 |

## 后果

**正面**

- 并发安全由数据库保证，不依赖代码正确性；测试可断言"10 并发只成功 1 条"
- 历史申请（已驳回/已撤回）不受影响，可保留完整的竞争记录用于统计
- 终审事务里的"驳回其余"只需一条 `UPDATE`，不需要遍历

**负面**

- 需要理解部分索引：`approved` 必须包含在索引条件里，否则终审通过后唯一索引释放，
  又会有新申请进来（业务上不希望——物品已经在交接流程中）
- SQLite 的部分索引在旧版本（<3.8）不支持；本项目要求 3.24+，已在 `probe/` 中验证
- `need_more` 也算"进行中"，语义上正确但评审时需要解释清楚
