# ADR-0001 采用分层架构 + 集成适配器

- **状态**：已接受
- **日期**：待填
- **决策人**：架构 / 设计工程师（人守关卡：架构决策须签字）

## 背景

系统需要对接三类外部系统：学校统一身份认证、对象存储、通知通道（微信 / 邮件）。
立项阶段的可行性判定结论是：这三类**在课程环境里都无法真正实测**（认证需应用登记与回调备案，
微信需 `openid` 与模板审核，存储需部署 MinIO）。若把调用逻辑直接写进业务代码，会出现两个问题：

1. 演示环境跑不通，业务代码无法测试；
2. 换到真实环境要改多处，评审时说不清"到底哪部分是模拟的"。

同时，业务侧的核心复杂度（认领审核状态机、并发互斥、脱敏）与外部系统无关，应该能独立测试。

## 决策

采用**前后端分离的分层架构**（表现层 / 接口层 / 应用层 / 领域层 / 集成层 / 基础设施），
并在集成层使用**适配器模式**：每个外部系统定义一个协议（`AuthProvider`、`ObjectStore`、`Notifier`），
提供"本地实现"与"生产实现"两套，由配置切换。

| 协议 | 本地实现（默认） | 生产实现 |
|---|---|---|
| `AuthProvider` | `LocalAuthProvider`（`auth_source=local`，演示账号） | `SsoAuthProvider`（OAuth2 授权码） |
| `ObjectStore` | `LocalDiskStore`（`var/objects/`） | `S3ObjectStore`（MinIO / OSS） |
| `Notifier` | `ConsoleNotifier`（写日志 + 落 `delivery_log`） | `WechatNotifier` / `SmtpNotifier` |

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 业务代码直接调外部 SDK | 起步快 | 演示环境跑不通；无法单测；换环境改多处 | 否决 |
| 适配器 + 配置切换 | 可测试、可演示、边界清晰 | 初期多一层抽象与两套实现 | **采纳** |
| 插件热加载 | 可动态扩展 | 复杂度高，课程项目不需要 | 否决 |

## 后果

**正面**

- 核心链路的单元测试不依赖网络，CI 稳定（NFR-2、NFR-3 可自动断言）
- 演示环境与生产环境同一套业务代码，只是适配器不同——答辩时能明确回答"哪部分是模拟的"
- 新增通知通道（如短信）只需加一个适配器，不改业务层

**负面**

- 需要维护两套实现，本地实现要保证语义与生产一致（例如本地通知也要写 `delivery_log`）
- 抽象层带来少量样板代码
- 本地实现可能"过于顺利"（比如本地存储从不超时），需专门写故障注入测试
