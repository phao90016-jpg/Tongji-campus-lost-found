## 构件 1：状态机引擎（DES-SVC-001）

### 职责

把"发布 / 认领申请 / 举报 / 认证"四类对象的状态迁移收敛到一处：
定义合法迁移表、校验、写状态日志。业务代码不允许直接 `UPDATE status`。

### 类设计

| 类 | 职责 |
|---|---|
| `models/enums.py` | `ItemStatus`、`ClaimStatus`、`ReportStatus`、`CertStatus` 四个 `StrEnum` |
| `services/state_machine.py` | `TRANSITIONS` 表、`ensure_transition(obj_type, from_, to)`、`transition(...)` |
| `services/audit.py` | `log_status(...)` 写 `item_status_log` |

### 关键算法

```python
TRANSITIONS = {
    "item": {
        "draft":          {"pending_review", "published"},
        "pending_review": {"published", "rejected"},
        "published":      {"claiming", "closed", "expired"},
        "claiming":       {"handed_over", "published"},
        "handed_over":    {"closed"},
    },
    "claim": {
        "pending_first": {"pending_final", "need_more", "withdrawn", "rejected"},
        "need_more":     {"pending_first", "rejected"},
        "pending_final": {"approved", "rejected", "need_more"},
        "approved":      {"completed", "expired"},
    },
    ...
}

def transition(conn, obj_type, obj_id, from_status, to_status, actor_id, reason=None):
    allowed = TRANSITIONS.get(obj_type, {}).get(from_status, set())
    if to_status not in allowed:
        raise ItemStateInvalid(f"{from_status} -> {to_status} 非法迁移")
    # 调用方负责在同一事务内 UPDATE ... WHERE id=? AND status=from_status
    log_status(conn, obj_type, obj_id, from_status, to_status, actor_id, reason)
```

**为什么把迁移表放在代码里而不是数据库**：迁移规则是领域不变量，改它等于改需求，应该走代码评审；
数据库只存当前状态与历史。状态历史在 `item_status_log`，可回溯。

### 异常与降级

| 异常 | 处理 |
|---|---|
| 非法迁移 | 抛 `ItemStateInvalid` → 接口层映射 409 `ITEM_STATE_INVALID` |
| 并发导致 `UPDATE` 影响行数为 0 | 抛 `ConcurrencyConflict` → 409，提示刷新重试 |
| 定时任务触发过期时对象已不是 `published` | 跳过并记 debug 日志，不报错 |

### 单元测试要点

- 每条合法迁移都能成功，且写一条状态日志
- 每条非法迁移抛异常且状态不变（参数化覆盖全部 `(from, to)` 组合）
- 并发两次 `published → claiming` 只有一次成功

## 构件 2：终审事务（DES-API-005）

### 职责

审核员给出终审结论。通过时必须在**一个事务**内完成：申请转已通过、生成交接码、
驳回其余进行中申请、发布转认领中、写状态日志与审计。任一步失败全部回滚。

### 关键算法

```python
def final_review(conn, claim_id, reviewer, decision, reason_code, comment):
    with tx(conn):                                  # BEGIN IMMEDIATE
        claim = load_claim_for_update(conn, claim_id)
        assert claim.status == "pending_final"
        assert reviewer.id not in (claim.applicant_id, claim.item_owner_id)
        ensure_transition("claim", claim.status, target_status)

        # 乐观锁：version 不匹配说明别人先处理了
        rows = conn.execute(
            "UPDATE claim_application SET status=?, version=version+1, "
            "final_reviewed_at=?, reject_reason_code=? "
            "WHERE id=? AND version=? AND status='pending_final'",
            (target_status, now, reason_code, claim_id, claim.version))
        if rows.rowcount == 0:
            raise ConcurrencyConflict("该申请已被处理")

        if decision == "approve":
            code = new_handover_code()
            insert_handover_token(conn, claim_id, sha256(code + str(claim_id)), now + 72h)
            # 同物品其余进行中申请一律驳回（事务内）
            conn.execute(
                "UPDATE claim_application SET status='rejected', reject_reason_code='taken_by_other' "
                "WHERE item_id=? AND id<>? AND status IN "
                "('pending_first','pending_final','need_more')", (claim.item_id, claim_id))
            conn.execute("UPDATE item SET status='claiming', version=version+1 "
                         "WHERE id=? AND status='published'", (claim.item_id,))
            log_status(...); log_audit(...)
            return {"code": code, "expires_at": ...}
```

### 并发与一致性

| 场景 | 保证 |
|---|---|
| 两个审核员同时点通过 | `version` 乐观锁 + `WHERE status='pending_final'`，只有一个 rowcount=1 |
| 申请人同时撤回 | 撤回语句带 `WHERE status IN ('pending_first','pending_final')`，先到先得 |
| 交接码生成失败 | 事务回滚，申请仍是 `pending_final`，可重试 |
| 驳回其余申请时有人正在提交新申请 | 部分唯一索引 `uq_claim_active` 挡住；提交方收到 409 |

### 单元测试要点

- 通过后：申请 `approved`、交接码存在、其余申请 `rejected`、发布 `claiming`、状态日志 2 条
- 驳回后：申请 `rejected`、发布仍 `published`、无交接码
- 同一申请终审两次：第二次 409
- 审核人 = 申请人：403
- 事务中途抛异常：数据库无残留（用 `pytest.raises` + 重新查询断言）

## 构件 3：交接码（DES-SVC-003）

### 职责

生成、重发、核销一次性交接码。码只存哈希；核销幂等；连续输错锁定。

### 关键算法

```python
ALPHABET = "ACDEFGHJKLMNPQRSTUVWXY23456789"   # 去掉易混字符 0/O/1/I/B/8

def new_code() -> str: return "".join(secrets.choice(ALPHABET) for _ in range(6))

def verify_and_consume(conn, claim_id, code, actor):
    with tx(conn):
        tok = conn.execute("SELECT * FROM handover_token WHERE claim_id=?", (claim_id,)).fetchone()
        if not tok: raise Forbidden()                       # 不泄露是否存在
        if actor.id not in (claim.applicant_id, claim.item_owner_id): raise Forbidden()
        if tok.consumed_at: raise HandoverConsumed()
        if now() > tok.expires_at: raise HandoverExpired()
        if sha256(code + str(claim_id)) != tok.code_hash:
            bump_fail_count(claim_id); raise Forbidden("交接码不正确")
        rows = conn.execute(
            "UPDATE handover_token SET consumed_at=?, consumed_by=? "
            "WHERE id=? AND consumed_at IS NULL", (now(), actor.id, tok.id))
        if rows.rowcount == 0: raise HandoverConsumed()      # 并发核销
        claim.status -> completed; item.status -> handed_over
```

**安全考量**

| 点 | 做法 | 理由 |
|---|---|---|
| 码长度 | 6 位，字母表 31 个字符 | 约 8.9 亿组合；配合"5 次锁定"足够 |
| 存储 | 只存 `sha256(code + claim_id)` | 库被拖走也无法直接使用 |
| 有效期 | 72 小时 | 覆盖"约好明天交接"的常见情形 |
| 重发 | ≤2 次，旧码立即作废 | 防止无限刷码试探 |
| 输错 | 5 次锁 30 分钟 | 防暴力枚举 |
| 展示 | 明文只在创建/重发响应里出现一次 | 之后双方从"我的申请"页查看掩码 + 重发 |

### 单元测试要点

- 正确码核销成功，重复核销 409
- 过期码 410；重发后旧码 410、新码可用
- 非相关方核销 403
- 并发 10 次核销同一码，只成功 1 次
- 输错 5 次后正确码也被锁定 423

## 构件 4：脱敏、字段可见性与审计（DES-SVC-002 / DES-SEC-002）

### 职责

统一决定"谁能看到什么字段"，并在敏感读取时写审计。业务代码不各自拼接脱敏逻辑。

### 类设计

| 类 | 职责 |
|---|---|
| `services/visibility.py` | `visible_fields(viewer, item) -> set[str]`；`mask_phone(v)` |
| `services/audit.py` | `log_audit(actor, action, target_type, target_id, detail)` |
| `api/deps.py` | `current_user`、`require(capability)` 依赖 |

### 关键算法

```python
def mask_phone(v: str | None) -> str | None:
    if not v: return v
    if len(v) <= 7: return v[0] + "*" * (len(v) - 2) + v[-1]
    return v[:3] + "****" + v[-4:]

def can_read_pii(viewer, target_user_id, related_claim=None) -> bool:
    if viewer.id == target_user_id: return True
    if "pii:read" in viewer.permissions: return True          # reviewer
    if related_claim and related_claim.status == "approved" and viewer.id in (related_claim.applicant_id, ...):
        return True                                            # 已通过终审的双方
    return False
```

**审计触发点（必须写）**

| action | 触发 | 记录字段 |
|---|---|---|
| `pii.read` | 读取他人手机号明文 | actor、target_user、场景（审核页/交接页） |
| `image.original.read` | 取原图预签名 URL | actor、item、image |
| `report.dispose` | 处置举报 | actor、report、action、理由 |
| `user.role.grant` | 授予/收回角色 | actor、target_user、roles |
| `config.update` | 改配置 | actor、key、旧值、新值 |
| `stats.export` | 导出报表 | actor、period、行数 |

> 审计 `detail` 只记元数据，**不记物品描述、认领理由、聊天文本**。这条在代码评审里查。

### 单元测试要点

- 学生读他人手机号 → `138****8000`
- 审核员读 → 原文，且 `audit_log` 多一条 `pii.read`
- 越权访问他人申请详情 → 403 且响应体不含 `reason` 字段
- 响应 JSON 序列化后全文搜索，不应出现完整 11 位手机号（用正则断言）

## 构件 5：通知投递编排与降级（DES-SVC-004）

### 职责

站内消息必达；按"微信 → 邮件 → 站内"顺序投递；每次尝试写记录；重启后补扫；不重复发送。

### 类设计

| 类 | 职责 |
|---|---|
| `integrations/notifier.py` | `Notifier` 协议 + `WechatNotifier` / `EmailNotifier` / `ConsoleNotifier` |
| `services/notify.py` | `enqueue(user, type, title, body)`、`tick()`、`deliver(delivery)` |

### 关键算法

```python
CHANNEL_ORDER = ("wechat", "email")     # 站内消息在 enqueue 时已写入，不需投递

def enqueue(conn, user_id, ntype, title, body, target=None):
    nid = insert_notification(...)                       # 站内必达
    for ch in CHANNEL_ORDER:
        if channel_enabled(conn, user_id, ch):
            insert_delivery(nid, ch, plan_at=now())      # 每个通道一条待投递

def tick(conn):
    rows = conn.execute("SELECT * FROM delivery WHERE status='pending' AND plan_at<=? "
                        "ORDER BY plan_at LIMIT 50", (now(),)).fetchall()
    for d in rows:
        if not claim_delivery(conn, d.id): continue       # UPDATE ... WHERE status='pending'
        try:
            ok = notifier_for(d.channel).send(d)
            log_attempt(conn, d, ok)
            finish(conn, d, "sent" if ok else "failed")
        except Exception as e:
            log_attempt(conn, d, False, err=e)
            finish(conn, d, "failed")                     # 降级：下一条通道已在队列里
```

**降级语义**：降级不是"同一时刻依次尝试"，而是"每个通道一条独立待投递记录，按优先级顺序发送"。
好处：微信失败时邮件那条本来就在队列里，不需要在失败分支里临时创建；坏处：可能两条都成功（用户收到两次），
因此约定"同一通知在任一通道成功后，其余通道置 `skipped`"。

### 异常与降级

| 异常 | 处理 |
|---|---|
| 微信凭据失效（`40001`） | 该通道置 `failed`，通道标记 `needs_rebind`，通知用户重新绑定 |
| 邮件超时 | 重试 2 次（指数退避 1s/3s），仍失败置 `failed` |
| 进程重启 | `tick()` 扫 `pending` 与 `sending` 超过 5 分钟的记录，后者回退为 `pending` |
| 全部通道失败 | 站内消息仍在，列表页可查；不抛错给业务调用方 |

### 单元测试要点

- 绑定微信+邮件 → 生成 2 条投递记录
- 微信失败 → 邮件成功 → 微信 `failed`、邮件 `sent`、站内消息可读
- 连续 `tick()` 两次不重复发送（`claim_delivery` 的乐观锁）
- 模拟重启（把 `sending` 改回）后 `tick()` 能补发

## 构件 6：图片遮蔽与预签名（DES-SEC-001）

### 职责

上传即压缩 + 生成遮蔽图；公开视图只给遮蔽图；原图必须换短期 URL；存储不可用时不影响发布。

### 关键算法

```
1. 解码 base64 → 校验 content_type ∈ {jpeg,png,webp}、大小 ≤2MB
2. Pillow 打开 → 按 EXIF 旋转 → 长边缩到 1600px → 存 JPEG(q=85) 为原图
3. 遮蔽图：整图 GaussianBlur(radius=8) → 缩到长边 800px
   （v0.3 改为 OCR 定位证件区域后只模糊该区域）
4. 写对象存储：items/{item_id}/{uuid}-orig.jpg、-masked.jpg
5. DB 记 original_key / masked_key；任一步失败 → status='pending'，发布照常成功
6. 取 URL：GET /items/{id}/images/{image_id}/url?variant=masked|original
   → 生成 HMAC 签名 + 10 分钟过期的查询串，返回相对路径
```

**为什么整图模糊而不是"提醒用户打码"**：用户不会打码。证件照一旦原图进公开列表，就等于泄露。
代价是特征看不清（影响认领判断），所以原图对审核员开放，由审核员在终审时比对。

### 异常与降级

| 异常 | 处理 |
|---|---|
| 图片格式不支持 / 超 2MB | 422 `VALIDATION_ERROR`，字段级提示 |
| 存储不可用 | 发布成功，`item_image.status='pending'`，详情页给重试入口（REQ-N-006） |
| 原图 URL 过期 | 403，前端自动重新申请 |
| 非授权角色取 `variant=original` | 403 + 审计（尝试记录也写） |

### 单元测试要点

- 上传后 `masked_key` 与 `original_key` 都存在且不同
- 普通用户取 original → 403；审核员取 → 200 且 `audit_log` 有记录
- 签名过期后重放 → 403
- 存储抛异常时发布仍 201，图片状态 `pending`
