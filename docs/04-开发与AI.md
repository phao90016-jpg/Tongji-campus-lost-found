## 开发顺序

1. 建用户、角色和演示登录。
2. 建发布、图片和检索。
3. 建认领申请和进行中唯一约束。
4. 建初审与终审。
5. 建领取确认、站内消息和审计。
6. 接真实外部集成，或者明确保留为模拟实现。

每一步按可演示功能合并，不先铺满全部接口。

## 质量门禁

- 需求或状态发生变化时，同步更新 `docs/02-需求.md` 和 `docs/03-设计.md`。
- 每条核心业务规则至少有一个正向测试和一个失败测试。
- 并发申请、越权访问、脱敏、重复领取确认必须有自动化测试。
- PR 至少一人复核，CI 通过后才能合并。
- 没有测试输出的功能，状态只能写“已实现”，不能写“已通过”。
- 没有真实授权和调用记录的外部接口，只能写“模拟”或“未接入”。
- 演示数据使用虚构姓名和虚构账号，不提交真实学号、手机号、证件照或密钥。

## AI 使用规则

AI 可以用于起草、整理、生成测试思路和检查文档一致性。AI 产出必须由人核对，代码必须运行测试。

不向 AI 提供密钥、真实学号、真实手机号、证件照或未公开的学校接口材料。AI 不负责最终需求确认、架构签字和合并放行。

## 已修正的文档问题

- 交接方式统一为“获准领取人确认已领取”，不再使用交接码。
- 手机号只允许本人或按案件授权的审核员查看，不再声称终审通过后双方自动可见。
- 同一物品从提交阶段就只允许一条进行中申请，不再保留“终审时驳回其他申请”的并行实现。
- 通知外部投递失败不影响业务结果，站内消息单独保存。
- 收藏、开放 API 和未定义功能从当前主干删除。
- 旧版中未发生的评审、迭代和 AI 返工记录不再写成事实。
