## 这个项目解决什么

### 一个失主的周三

| 时间 | 她在干什么 | 卡在哪 |
|---|---|---|
| 8:00 | 在图书馆三楼自习，校园卡放在桌角 | — |
| 9:00 | 回到宿舍，发现卡不见了 | 想不起来是在图书馆还是食堂丢的 |
| 9:10 | 在班级群发"求扩散：校园卡丢了" | 群里三小时后就刷不到这条 |
| 12:00 | 看到校园墙有人发"捡到校园卡" | 私聊问"是不是我的"，对方说"你说说特征" |
| 12:30 | 说"蓝色卡套" | 另外三个人也说是蓝色卡套，谁都不服 |
| 18:00 | 放弃了，去补办 | 补办排队 40 分钟，还花了 20 元 |

这一天里，**信息是有的，缺的是"证明东西是我的"这条通道**。

### 三件事，每件都有人吃亏

| 事 | 现在怎么做 | 谁吃亏 | 为什么拦不住 |
|---|---|---|---|
| 招领信息三小时被刷走 | 群消息、校园墙 | 失主 | 没有结构化检索，翻不回去 |
| 认领靠"说说特征" | 私聊、对质 | 真失主、拾取者 | 特征谁都能编，没有可核验的凭证 |
| 联系方式公开发在群里 | 留手机号、发证件照 | 双方 | 撤不回来，也没人负责脱敏 |

### 现有渠道为什么不够

| 渠道 | 它解决了 | 它没解决 |
|---|---|---|
| 班级群 / 年级群 | 有人看见 | 会刷走；重复发；无法检索 |
| 校园墙 / 二手群 | 覆盖广 | 没有结构；谁都能私聊；无法验证身份 |
| 保卫处登记簿 | 权威、集中 | 只在工作时间；失主基本不会去查；认领靠自述 |
| 现有失物招领小程序 | 能发布能检索 | 大多止步于"留联系方式"，认领仍是线下自述 |

### 这个项目怎么做

```
① 登记            ② 核验认领              ③ 交接留痕
失物/招领发布  →  核验问题 + 拾取者初审  →  一次性交接码
分类地点检索      审核员终审（看原图/历史）    双方任一方核销
```

1. **登记**：失主发"我丢了什么"，拾取者发"我捡到了什么"；招领必须带 1–3 个只有真失主能回答的核验问题。
2. **核验认领**：失主提交申请并回答核验问题 → 拾取者初审（他知道自己捡到的是什么）→ 保卫处审核员终审（他能看原图、申请人历史与信用分）。
3. **交接留痕**：终审通过生成 6 位一次性交接码，线下凭码核销，状态才落"已交接"；其余排队申请自动驳回。

### 三个设计判断

1. **认领必须双人把关，不能一个人说了算。** 拾取者只知道自己捡到了什么，不知道申请人是不是失主；审核员有权限看原图与历史，但不在现场。两关都过才交接，是对 R1（冒领）唯一有效的应对。
2. **敏感信息在序列化层统一脱敏，不靠用户自律。** 手机号默认 `138****8000`；证件照入库即生成遮蔽图，原图只有审核员能取，且走 10 分钟预签名 URL + 审计。
3. **同一物品的"进行中申请"由数据库保证唯一，不靠应用层判断。** 部分唯一索引 `uq_claim_active` 让并发下也不可能出现两条进行中申请——这是 R3（并发冲突）的硬约束。

## 功能

六组功能、**27 项功能需求**，分三个增量交付。详细规约见 [SRS v1.0](docs/02-需求规约/SRS-v1.0.md) 与 [选题文稿](docs/00-立项/选题文稿.md) 第三节。

| 组 | 解决什么 | 关键能力 | 增量 |
|---|---|---|---|
| 1 身份与账号 | 谁在操作 | 统一认证登录、拾取者实名认证、联系方式可见性 | v0.1 / v0.2 |
| 2 发布与内容治理 | 东西怎么登记 | 失物/招领发布、核验问题、图片遮蔽、发布前校验 | v0.1 |
| 3 检索与匹配 | 怎么找到 | 分类/地点/时间浏览、关键词检索、相似推荐、关键词订阅 | v0.1 / v0.2 / v0.3 |
| 4 认领与审核 | 凭什么给 | 提交/撤回申请、拾取者初审、审核员终审、交接码核销 | v0.1 |
| 5 状态流转、举报与信用 | 出问题怎么办 | 状态机与自动过期、举报、处置、信用分、申诉 | v0.1 / v0.2 |
| 6 通知、统计与后台 | 跑得下去 | 多通道通知与降级、审核工作台、统计看板、RBAC 与审计 | v0.2 |

**状态机**：发布 `草稿 → 待审核 → 公示中 → 认领中 → 已交接 → 已关闭`（可转已驳回/已过期）；
申请 `待初审 → 待终审 → 已通过 → 已完成`（可转待补充/已驳回/已撤回/已失效）。
非法迁移返回 409，每次迁移写状态日志。见 [状态图与顺序图](docs/03-需求分析模型/状态图与顺序图.md)。

**信用分**：初始 100；警告 −10、虚假发布 −30、冒领 −40；低于 60 不能发布招领，低于 40 不能提交认领申请。

## 角色与权限

| 角色 | 代码 | 职责 | 数据边界 |
|---|---|---|---|
| 学生（失主 / 浏览者） | `student` | 检索、发布失物、提交认领、举报 | 仅本人完整信息；他人手机号脱敏 |
| 拾取者 | `finder` | 发布招领、初审认领、登记保管、核销交接码 | 本人招领的申请；申请人手机号不可见 |
| 审核员（保卫处） | `reviewer` | 终审、处置举报、审核认证、维护基础数据 | 全域只读 + 审核动作；原图可见；操作全审计 |
| 系统管理员 | `admin` | 用户与角色、配置、审计 | 全局配置；默认不读物品正文 |
| 定时任务 | `system` | 自动过期、超时升级、通知补扫 | 只写系统字段，不代替人工审核 |

权限模型：**RBAC + 能力判定 + 资源归属校验 + 字段级脱敏**。代码判定能力（`claim:review_final`），角色只是能力集合。
越权统一返回 403，且不区分"不存在"与"无权限"。详见 [概要设计](docs/04-设计/概要设计.md) §4.1。

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite | 学生端 / 拾取者端 / 审核后台同仓 |

| CI | GitHub Actions | ruff + pytest，红灯禁合并 |

## 快速开始

> 骨架期只验证后端能起来、CI 是绿的。业务代码自 v0.1 起按 Issue 增量交付。

```bash
# 后端
cd src/backend
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
cp .env.example .env               # 填密钥；.env 不提交
pytest -q                          # 应全绿
uvicorn app.main:app --reload      # http://localhost:8000/health

# 前端（骨架）
cd src/frontend
npm install
npm run dev
```

```bash
# 渲染模型图（需要 java + plantuml.jar，见 scripts/README.md）
python scripts/render_models.py

# Markdown → docx（课程交付物）
python scripts/md2docx.py docs/00-立项/选题文稿.md docs/00-立项/选题文稿.docx
```

## 工程约定

完整工作流见 **[CONTRIBUTING.md](CONTRIBUTING.md)**，要点：

- `main` 受保护，**禁止直推**，一律走 Pull Request
- 每个 PR 至少 1 人 Review + CI 绿灯方可合并
- 需求、缺陷、任务一律先建 Issue；变更走"申请 → 评审 → 批准 → 关闭"
- AI 产出必须登记到 [AI 使用台账](docs/08-AI使用/AI使用台账.md)；密钥、token、真实学工号严禁进入仓库与提示词
- 文档改动同时更新 Markdown 与 docx（`python scripts/md2docx.py …`）
- 禁止"最后一晚打包上传"式提交，提交分布计入过程成绩
