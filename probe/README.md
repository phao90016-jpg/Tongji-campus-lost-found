# 可行性探测（probe）

立项阶段对"选题里的技术假设到底成不成立"做的实测，不是读文档后的推测。

## 为什么在这里

选题文稿里有四条硬假设：

1. 中文能检索（"校园卡"要能搜到"饭卡"之外的说法）——如果 FTS5 不支持中文分词，检索方案要换；
2. 同一招领在并发下只能有一条进行中申请——如果部分唯一索引不可用，得改用分布式锁；
3. 图片遮蔽的耗时与体积可接受——如果一张证件照要处理 5 秒、压不到 100KB，上传体验就崩了；
4. 文档里的图能自己生成——如果要靠在线网站画，图就没法版本化。

这四条都能在本机验证。与其在需求阶段假设，不如把脚本与结果一起入库：结论可复跑、可复核，评审时能当场跑一遍。

## 文件

| 文件 | 内容 |
|---|---|
| `probe_feasibility.py` | 4 项实测：FTS5 中文检索、并发互斥、图片遮蔽、渲染链路 |
| `probe_result.json` | 最近一次实测结果（时间戳 + 逐项数据） |

## 怎么跑

```bash
python probe/probe_feasibility.py            # 人读表格
python probe/probe_feasibility.py --json     # 写 probe_result.json
```

只依赖标准库；P3 需要 Pillow（`pip install pillow`），没装会跳过并标注。

## 最近一次结论（2026-11-26）

环境：Windows 10 / Python 3.12.14 / SQLite 3.53.1 / 本机 SSD。

| 项 | 结果 | 对设计的含义 |
|---|---|---|
| **P1 FTS5 可用性** | ✅ 可用，索引 10000 条 | 检索方案成立 |
| **P1 中文检索** | ✅ 字符级拆词 + 短语匹配，命中数与 `LIKE` 完全一致（966/966） | 不需要引入外部分词器，也不需要 `zhparser` |
| **P1 性能** | P95：FTS5 **12.86 ms**，`LIKE` **51.36 ms**，列表查询 **2.87 ms**（1 万条） | 距 REQ-N-001 的 800ms 有 60 倍余量 |
| **P2 部分唯一索引** | ✅ 支持（SQLite 3.53） | ADR-0002 成立 |
| **P2 并发互斥** | ✅ 10 线程：成功 **1**、冲突 **9**、其他 0，进行中记录数 **1** | NFR-2 可用数据库保证，不依赖应用层判断 |
| **P3 图片遮蔽** | 源图 186.7 KB → 原图 29.9 KB + 遮蔽图 8.0 KB，耗时 **1074.9 ms** | 耗时偏高（大尺寸纯色图 + 高斯模糊），但异步补传后不影响发布（REQ-N-006）；v0.1 需测真实照片 |
| **P4 渲染链路** | java 可用；`plantuml.jar` **不入库**，需放 `scripts/tools/` 或设 `PLANTUML_JAR` | 渲染产物已提交到 `docs/assets/`，评审无需 java |

### 未实测（必须写清楚）

| 项 | 为什么没测 | 影响 |
|---|---|---|
| 学校统一身份认证 | 需要应用登记、回调地址备案与 scope 审批 | v0.1 用本地账号兜底（`auth_source=local`），接口契约不变（R10） |
| 微信服务号模板消息 | 需要 `openid`、模板审核与额度 | 用 ConsoleNotifier 走同一套降级链，演示效果等价（R4） |
| 对象存储预签名 URL | 需要部署 MinIO 或云 OSS | 本地磁盘 + HMAC 签名模拟，语义一致（ADR-0001） |
| 1 万条真实业务数据的端到端检索 | 需要 v0.1 后端 | 本脚本只测存储层，端到端 P95 在 v0.1 的测试报告里补 |

> 诚实原则：没实测就写"未实测"。把"模拟"和"真实"分清楚，比写一个漂亮的假数字有用。

## 注意

- 脚本里的数据全部随机生成（种子固定 20261126，可复现），不含任何真实个人信息
- P3 造的是纯色大图，真实手机照片的耗时与体积会不同，需在 v0.1 用真图复测
- 结论变化时同时更新本文件与 [选题文稿 §15.1](../docs/00-立项/选题文稿.md)
